- Q: 觸發範圍？ → A: **D4＝一體適用**——凡 admin 經手設定的密碼（建帳＋重設手輸＋隨機）一律觸發；seed 三帳號與 015 前既有帳號零記錄不補；admin 對自己重設＝本人改（不觸發）。

- Q: 改完後？ → A: **D6＝立即登出重登**（前端登出達成；後端改密語意零偏差、ADR 0055 keep-sid 不變式字面維持）。
- Q: 設密頻率？ → A: **D7＝N 秒冷卻**（同一操作者對同一標的、距上次成功設密未滿 N 秒即拒；N＝系統設定可調、預設 60、0＝停用；僅限制成功設密、失敗嘗試不計）。
- Q: B-103 順路評？ → A: **D8＝不提煉**＋收刀時條目觸發措辭釐清為「觸及 email/phone 雙卡本體時」。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理員經手設密→會員首登強制換密 (Priority: P1)

管理員在使用者管理頁替會員設定密碼（建帳指定、重設手輸、或隨機產生）後，該會員以此密碼**首次登入成功即被強制導向「重設密碼」專頁**：無論直輸網址、重新整理、深連結，都回到該頁；且未換密前**整個 API 面被封鎖**（除改密必需操作外一律拒絕，含繞過瀏覽器以工具直打）。會員完成改密（驗舊密＝剛登入的密碼、新密碼過政策）後**立即被登出回登入畫面**，持新密碼重新登入後暢行無阻。

**Why this priority**: B-030 條目本體、ADR 0055 殘餘義務的兌現標的；「admin 知悉的密碼必須以本人換密收場」＝本刀核心安全語意。

**Independent Test**: admin 對測試會員按「重設密碼」設一組密碼→該會員登入→驗證被導向強制改密頁＋以 token 直打列表 API 被拒→改密成功→自動登出→新密碼重登→暢行且判定清除。

**Acceptance Scenarios**:

1. **Given** admin 以任一入口（建帳／重設手輸／隨機）替會員設密，**When** 會員以該密碼登入，**Then** 直接落在強制改密頁；點選單、直輸網址、重新整理皆被導回。
2. **Given** 會員處於強制換密狀態且持有效 token，**When** 以工具直打非白名單 API（如使用者列表），**Then** 被明確業務拒因拒絕；改密、密碼政策、個人識別資訊、路由查詢、登出、憑證換發不受影響。
3. **Given** 會員於強制改密頁完成改密（舊密正確＋新密過政策），**When** 成功，**Then** 立即登出回登入頁；持新密碼重登後不再被導向、API 面全開。
4. **Given** 會員在強制改密頁輸入錯誤舊密碼或違政策新密碼，**When** 送出，**Then** 得到與自助改密一致的逐項明確拒因；狀態不變。
5. **Given** admin 對**自己**重設密碼，**When** 送出成功，**Then** 不觸發任何強制換密（本人改語意）；下次登入照常。
6. **Given** seed 三帳號（Super/Admin/User）或 015 上線前既有帳號，**When** 登入，**Then** 不受任何強制換密影響（demo 零阻礙）。
7. **Given** 會員處於強制換密狀態，**When** admin 再次重設其密碼，**Then** 會員以新密碼登入仍被強制換密（他人經手記錄仍在）。
8. **Given** 會員在強制改密頁，**When** 點「登出」，**Then** 登出回登入頁（不改密）；再次登入仍被導向強制改密頁。

### User Story 2 - 隨機密碼產生浮層（三掛載點） (Priority: P2)

管理員或會員需要一組符合密碼政策的隨機密碼時，按「隨機密碼」／「密碼」鈕浮出產密層：按「產生」得到一組隨機密碼（唯讀顯示、可切換明文顯示、可一鍵複製）。三個掛載點：①使用者管理「新增使用者」抽屜密碼欄旁（帶入密碼欄）②使用者管理列表操作欄「密碼」動作（隨機專用、浮層內確認送出＝重設該會員密碼並觸發首登換密）③個人中心改密卡儲存前（帶入新密碼＋確認新密碼兩欄、走自助改密流程、不觸發強制）。隨機值一律在使用者瀏覽器本地產生，伺服器回應恆不含密碼。

**Why this priority**: B-030「隨機生成」半件的兌現；依賴 US1 的觸發語意（掛載點②）但產密工具本身獨立可測。

**Independent Test**: 三掛載點各按「產生」→值符合現行密碼政策（含長度、字元類別、不含帳號名）→複製鈕取得同值→帶入欄位後照各自流程送出成功。

**Acceptance Scenarios**:

1. **Given** 任一掛載點浮層，**When** 按「產生」，**Then** 得到符合現行密碼政策全部規則的隨機值；連按兩次值不同；可切換明文顯示、可複製。
2. **Given** 新增使用者抽屜，**When** 浮層帶入後送出建帳，**Then** 建帳成功且該會員首登被強制換密。
3. **Given** 操作欄「密碼」動作浮層，**When** 未按「產生」，**Then** 無法送出（輸入區唯讀、不可手輸）；按「產生」後確認送出＝重設該會員密碼、成功提示與既有重設一致。
4. **Given** 個人中心改密卡，**When** 浮層帶入新密碼＋確認欄並以正確舊密碼儲存，**Then** 自助改密成功（撤他裝置照舊）、**不**觸發本人任何強制換密；帶入值以明文顯示供抄存。
5. **Given** 任一掛載點完整流程，**When** 檢視全部網路回應，**Then** 回應內容不含密碼明文（產生動作零網路請求）。

### User Story 3 - 設密冷卻（頻率保護） (Priority: P3)

同一操作者對同一標的帳號成功設密後 N 秒內再次設密（任一入口），系統以明確拒因拒絕；N 由系統設定頁調整（預設 60 秒、0＝停用）。不同操作者對同一標的互不影響；失敗的設密嘗試不啟動冷卻。

**Why this priority**: user 親決的頻率保護（D7）；獨立於主流程可測、影響面小。

**Independent Test**: admin 對同一會員連續兩次重設（間隔小於 N）→第二次被拒且提示明確；調 N=0 後同操作不再被拒。

**Acceptance Scenarios**:

1. **Given** admin 剛成功重設某會員密碼，**When** N 秒內對同一會員再次重設（手輸或隨機），**Then** 被明確拒因拒絕且提示含剩餘秒數；密碼與狀態不變。
2. **Given** 冷卻拒絕發生，**When** 等待滿 N 秒後重試，**Then** 成功。
3. **Given** 系統設定頁將冷卻秒數改為 0，**When** 連續設密，**Then** 不受限制；改回正值即恢復限制。
4. **Given** admin A 剛重設某會員，**When** admin B 於 N 秒內重設同一會員，**Then** 成功（冷卻按操作者×標的對計）。
5. **Given** 會員自助改密因舊密錯誤失敗，**When** 立即重試（正確舊密），**Then** 不受冷卻影響（失敗不計）。
6. **Given** 會員處於強制換密狀態且其自改記錄距今未滿 N 秒（自鎖窗），**When** 於強制頁送出改密，**Then** 被冷卻拒絕且提示含剩餘秒數；滿 N 秒後重試成功（零例外、user 親決）。

### User Story 4 - 介面三語化 (Priority: P4)

本刀全部新介面文字（產密浮層、操作欄「密碼」動作、強制改密頁、冷卻與強制換密拒因、系統設定新項標籤）支援 zh-TW／zh-CN／en-US 三語，切語系零 raw key；zh-TW 為在地化正體用語。

**Why this priority**: rev4 三語紀律例行兌現；獨立可驗。

**Independent Test**: 三語系各切換一次，走完 US1 全流程與三掛載點浮層，零 raw key、用語正確。

**Acceptance Scenarios**:

1. **Given** 語系 en-US，**When** 會員走完首登強制換密全流程，**Then** 全部介面與提示（含強制換密拒因、登出後提示）為英文。
2. **Given** 語系 zh-TW，**When** 開任一掛載點浮層與系統設定頁新項，**Then** 用語為在地化正體、零 raw key。

### Edge Cases

- 並發：兩 admin 同時對同一會員設密／會員自助改密與 admin 重設同時發生→序列化處理、後到者依既有語意誠實處置（誤差終態偏「多強制一次」＝fail-safe、絕不誤放行）。
- admin 重設「當下持有活躍 session」的會員→該會員全部 session 依既有語意即時撤銷（下一請求即被登出），再登入才進入強制換密；不存在「舊 session 半鎖半通」中間態。
- 強制換密狀態下深連結到不存在的頁面→路由存在性查詢屬白名單、不炸錯，最終仍落在強制改密頁。
- 強制頁上以浮層產生隨機值、未抄存即送出→改密成功、登出後使用者不知新密碼→復原路＝admin 重設（再度強制換密）；浮層於此情境強調「複製後送出」。
- 會員被軟刪→經手記錄不清（登入本被活性判定擋下）；復原後判定沿刪前狀態（密碼未變、語意合理）。
- 改完密碼後未登出的殘留 token（使用者自行中斷流程）→判定已清除、其為合法使用者，無安全缺口。
- 冷卻自鎖窗（本人自改後 N 秒內被 admin 重設→強制頁改密遭冷卻拒）→拒絕提示顯示剩餘秒數、最長 N 秒自癒（user 親決不豁免、零例外）。
- 系統設定冷卻鍵被刪或讀取失敗→以預設值運作（fail-default）、不阻斷設密。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 於每次密碼設定成功時記錄「操作者→標的」經手事實；判定規則單一：標的名下存在任一筆「操作者≠標的」記錄→該帳號登入後處於強制換密狀態；僅本人自改記錄或零記錄→不強制。判定 MUST 為登入後動態求值（非簽發時快照）。
- **FR-002**: 經手記錄範圍 MUST 一體適用：建帳指定初始密碼、管理員重設（手輸或隨機）皆記為他人經手；admin 對自己重設＝本人改；seed 帳號與本功能上線前既有帳號 MUST 零記錄（不回填、不強制）。
- **FR-003**: 本人改密成功（自助或強制頁）MUST 於同一原子操作內：清除本人名下**全部**經手記錄（範圍恆＝標的名下、絕非操作者名下）＋寫入一筆本人自改記錄；他人經手設密 MUST 於同一原子操作內完成密碼更新與經手記錄寫入（同操作者×標的重複設密＝刷新時間、每對至多一筆）。
- **FR-004**: 強制換密狀態下，前端一切頁面導航（含直輸網址、重新整理、深連結）MUST 被導向強制改密專頁；該頁 MUST 任何角色可達且不經選單曝光，並 MUST 提供「登出」退路（登出回登入頁；再登入仍被強制、語意不變）。
- **FR-005**: 強制換密狀態下，已認證 API 面 MUST 僅放行改密必需操作（改密、密碼政策讀取、本人身分資訊、路由樹與路由存在性查詢），其餘一律以明確業務拒因拒絕（含繞過前端之工具直打）；登出與憑證換發 MUST 不受影響。白名單語意 MUST 同時覆蓋一般已認證與帶權限管理端點（有管理權的被強制者亦不得使用管理功能）。
- **FR-006**: 強制頁改密成功後 MUST 立即登出並回登入頁；持新密碼重新登入後 MUST 暢行（判定已清除）。
- **FR-007**: 強制頁改密 MUST 完整複用既有自助改密驗證序（帳號存在→兩次一致→舊密正確→新≠舊→政策明細）與密碼政策單一驗證點（零分叉）；改密撤他裝置 session、保留當前操作 session 的既有語意 MUST 不變（登出由前端於成功後另行發起）。
- **FR-008**: 隨機密碼 MUST 於使用者端本地產生（密碼學安全亂數）、產生值 MUST 構造性滿足現行密碼政策全部規則（含不與帳號名相同）；伺服器回應 MUST 恆不含密碼；浮層 MUST 提供唯讀顯示、明文顯示切換、一鍵複製、帶入。
- **FR-009**: 使用者管理操作欄 MUST 新增「密碼」動作＝隨機專用浮層（不可手輸、僅可產生後確認送出、送出走既有重設密碼通道）；其按鈕可見性 MUST 沿用既有「重設密碼」權限碼（兩入口同進退、零新權限配置）；既有「重設密碼」手輸對話框 UI MUST 零改動；「新增使用者」抽屜與個人中心改密卡 MUST 各掛「隨機密碼」鈕（帶入對應欄位、後續流程照舊）。
- **FR-010**: 同一操作者對同一標的距上次**成功**設密未滿 N 秒的再次設密 MUST 以明確拒因拒絕；N MUST 為系統設定（管理頁可調、預設 60 秒、0＝停用、讀取失敗以預設值運作）；失敗嘗試 MUST 不啟動冷卻；冷卻檢查 MUST 排在各端點既有拒因全過之後（不重排既有驗證序、不入密碼政策單一驗證點）。冷卻 MUST 一體適用零例外（含強制換密狀態下的本人改密）；冷卻拒絕提示 MUST 攜剩餘秒數（各入口一致）。
- **FR-011**: 本刀全部新介面文字 MUST 三語支援（zh-TW 在地化正體）、切語系零 raw key、型別鏡像機器一致。
- **FR-012**: 前端對上游基線既有檔的改動 MUST 遵循 fork-delta 修改型 inline 紀律（原行逐字標記）；新檔走新增型圈界。
- **FR-013**: 強制換密判定 MUST 隨登入者身分資訊下發供前端導向（增量欄位、不動既有凍結契約形）；強制頁取用帳號名 MUST 為真實帳號（非暱稱別名）。
- **FR-014**: 並發情境（多 admin 同標的設密、自改×重設）MUST 序列化處理；前提失效時誠實拒絕、絕不假報成功；race 終態偏向「多強制一次」（fail-safe）、絕不誤放行。
- **FR-015**: 經手記錄 MUST 不含密碼任何形式（明文／雜湊）；本刀 MUST 不新增任何密碼洩漏面（日誌、稽核、回應皆沿既有遮蔽紀律）。
- **FR-016**: 會員軟刪 MUST 不清其經手記錄；復原後判定沿刪前狀態。

### Key Entities *(include if feature involves data)*

- **密碼經手記錄**: 「誰幫誰設了密碼」的狀態事實——標的帳號、操作者、最後設定時間；每（標的×操作者）至多一筆；不存密碼本體；本人自改記錄長存（兼「最後本人改密時間」、為未來密碼有效期留錨）、他人經手記錄於本人改密時清除。
- **設密冷卻設定**: 系統設定新項（秒數、0＝停用）；管理頁可調、預設 60。
- **強制換密判定投影**: 登入者身分資訊的增量布林欄——由經手記錄動態求值、供前端導向與 API 閘共用同一判定規則。

## Success Criteria *(mandatory)*

- **SC-002**: 強制換密狀態下以 token 直打非白名單 API 的成功率 0%（自動化與實彈驗證）；白名單內操作 100% 可用。
- **SC-003**: 強制頁改密成功後 100% 立即登出；新密碼重登後 100% 暢行；此清除語意有自動化測試背書（拆清除邏輯即紅）。
- **SC-004**: 本人自助改密（含用隨機值）觸發強制換密的比率 0%；seed 三帳號與存量帳號受影響比率 0%；admin 自我重設觸發比率 0%。

- **SC-008**: 判定規則三態（零記錄／純自改／含他人經手）各有自動化測試背書；經手記錄結構性無密碼欄。

## Assumptions

### 既有資產（已核實、2026-07-17 四鏡頭偵察＋對抗審查）

- 014 自助改密全鏈（固定五拒因序、密碼政策單一驗證點 ADR 0054、keep-sid 撤他裝置、8888 靜默登出管線）現成可複用——強制頁後端零新端點。
- 管理面既有入口齊備：建帳密碼欄（新增模式）、重設密碼輕量對話框、操作欄動作模式；改既有會員密碼唯一後端通道＝重設密碼（更新使用者無密碼欄）。
- 免選單曝光的頁面機制（constant route 靜態併集）現成——強制改密頁比照登入系頁面、後端路由面零改動。
- 使用者域寫端統一序列化鎖（島 I1）覆蓋設密全部路徑（建帳除外＝新列不可見豁免）——經手記錄寫入與密碼更新同交易原子。
- 密碼三重不洩（島 I5）既有紀律：DTO 遮蔽、稽核白名單、回應結構性排除；存取日誌絕不讀 body。
- 新表治理軌道現成：憲法變體 C 先例＋schema-gate 表級白名單（ADR 0039）＋settings seed 白名單（先例 m003/m005）；migration 次號 m011。

### 設計取捨（有意識接受）

- 「隨機密碼有效期」不做——經手記錄留最後設定時間為錨、屆時另刀免改表。
- B-102（改密舊密暴力試節流）不做——冷卻僅限制成功設密頻率、失敗嘗試不寫記錄不受冷卻，**非其替代**；照 roadmap 留 auth 延伸組。
- 前端請求攔截器兜底（強制換密拒因→自動導頁）不做——憲法攔截器控制流禁令；「admin 重設活躍 session」情境已由既有 8888 撤銷管線覆蓋（重設即全撤、殘留分頁下一請求即登出），兜底價值稀薄。
- 存量帳號不回填經手記錄——上線前的設密史無從辨識、demo 情境可接受；明文劃界。
- 強制頁保留隨機鈕（同元件零成本）——「產生未抄存即送出→鎖出」風險以 UX 強調收斂、復原路＝admin 重設。
- 冷卻拒發生於鎖內＝舊密雜湊已於鎖外算完才拒（既有固定序保序的代價、可接受）。
