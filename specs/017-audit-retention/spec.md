## User Scenarios & Testing *(mandatory)*

### User Story 1 - 稽核資料按保留政策自動清理（遵憲自記） (Priority: P1)

維運者設定（或沿用預設的）每表保留天數後，常駐背景作業每輪自動刪除四類稽核資料
（操作日誌／存取軌跡／登入嘗試／會話事件）中超過保留天數的舊列；每次每表的刪除都在
操作稽核中留下一筆系統身分的 PURGE 紀錄（含刪除筆數、0 筆照記）。

**Why this priority**: 本刀存在理由——016 只落了容量告警、沒有自動清理；沒有本故事其餘皆空。
遵憲自記（島 J3）是刪除合法性的構成要件、與刪除行為不可分。

**Independent Test**: 注入四表 backdate 超齡列與水平線內列 → 跑 execute → 超齡列消失、
線內列保留、op-log 出現四筆系統身分 PURGE 自記（payload 含表名／天數／筆數／作業標識）。

**Acceptance Scenarios**:

1. **Given** 四表各有超過與未超過保留天數的資料列，**When** 自動清理 execute 執行，
   **Then** 僅超齡列被刪除、未超齡列完整保留，且每表恰一筆 PURGE 自記落於操作日誌
   （同交易——「刪了沒記／記了沒刪」不可達）。
2. **Given** 某表零超齡列，**When** execute 執行，**Then** 該表零列被刪且仍落一筆
   deleted_count=0 的 PURGE 自記（J3「0 列照落」）。
3. **Given** 操作日誌中存在歷史 PURGE 類型列（手動或自動），**When** 對操作日誌源清理，
   **Then** PURGE 列一律豁免不刪（後設證據永久保留）。
4. **Given** 自記列剛落地，**When** 同輪或後續清理，**Then** 自記列（建立時間＝現在）
   天然在水平線之後且屬 PURGE 豁免，恆不落刪除範圍。
5. **Given** 管理者於稽核中心查詢操作日誌，**When** 檢視自動清理自記列，**Then** 可辨識
   其為系統作業（無人類操作者）且明細含作業標識，與手動 purge 列可區分。

### User Story 2 - 保留天數設定與安全防呆 (Priority: P2)

維運者以部署設定（env 四鍵）逐表調整保留天數；設定缺席時退預設 90 天；設定畸形時警示後退
預設；任一表明確設定低於 30 天下限時，整個作業拒絕執行——零刪除、結構化錯誤、不推成功心跳。

**Why this priority**: 錯誤設定下的行為決定了這把「自動刪資料的刀」可不可信；
防呆語意是 P1 可以安全上線的前提。

**Independent Test**: 分別以缺席／畸形／低於下限三種設定跑作業，驗證三分語意
（90 照跑／warn+90 照跑／前置全拒零動作）。

**Acceptance Scenarios**:

1. **Given** 四鍵全缺席，**When** 作業執行，**Then** 每表以 90 天保留跑完（fail-default）。
2. **Given** 某鍵值畸形（非正整數），**When** 作業執行，**Then** 發出警示事件後該表以
   90 天照跑（不阻斷）。
3. **Given** 任一鍵明確設定低於 30，**When** 作業啟動，**Then** 開跑前即拒——四表零刪除、
   結構化錯誤、非零退出、不推成功心跳（其後告警⑥於兩天內轉紅＝fail-loud 閉環）。
4. **Given** 某鍵恰等於 30，**When** 作業執行，**Then** 屬合法值、該表以 30 天保留照跑。

### User Story 3 - 失效可觀測（心跳、告警、不互踩） (Priority: P3)

維運者在 retention 作業停止運作或姿態誤配（只跑 dry-run 沒跑 execute）時，於兩天內收到
告警；本作業與既有 token 回收作業的心跳互不覆蓋；升級後既有告警不因舊心跳殘留而誤報。

**Why this priority**: 自動清理「靜默失效」的後果是稽核表無限增長——觀測閉環是本刀
長期可靠性的保證；但無 P1 則無物可觀測。

**Independent Test**: 推送舊時戳心跳→告警⑥轉紅→真跑 execute 復歸；清掉 execute 心跳僅留
dry-run→⑥b 轉紅；兩作業先後推心跳→雙方序列俱在。

**Acceptance Scenarios**:

1. **Given** retention 作業超過兩天未成功完跑，**When** 告警評估，**Then** 心跳逾時告警（⑥）
   轉紅並投遞。
2. **Given** dry-run 心跳在場而 execute 心跳缺席，**When** 告警評估，**Then** 誤配告警（⑥b）
   轉紅；一次 execute 完跑後復歸。
3. **Given** token 回收與 retention 兩作業於同輪先後完跑，**When** 檢視心跳，**Then** 兩組
   心跳序列俱在、互不覆蓋（各自分組）。
4. **Given** 系統從僅有 token 回收心跳的版本升級，**When** 依遷移步驟一次性清除舊心跳分組
   並重跑兩作業，**Then** 既有心跳告警（⑤／⑤b）與新告警（⑥／⑥b）皆處於正確狀態、無誤紅。
5. **Given** 心跳收集端不可達，**When** 作業完跑，**Then** 刪除結果不受影響、退出碼不變
   （心跳 best-effort）。

---

### User Story 4 - 手動姿態與既有功能零回歸 (Priority: P4)

維運者可一次性手動執行 dry-run（看逐表候刪數、零資料變動、不自記）或 execute；
既有手動 purge 端點與 token 回收作業行為完全不變。

**Why this priority**: dry-run 是上線前的安全觀察窗；零回歸是併入既有 reaper 底座的
基本要求。

**Independent Test**: 手動 dry-run 前後四表列數與 op-log 列數零變化且回報候刪數；
手動 purge 端點與 token 回收全既有測試零轉紅。

**Acceptance Scenarios**:

1. **Given** 四表有超齡列，**When** 手動 dry-run，**Then** 回報逐表候刪數、四表與操作日誌
   列數零變化（不自記）、推 dry-run 心跳。
2. **Given** 未知作業名，**When** 手動執行，**Then** 非零退出＋結構化錯誤（既有 fail-loud
   契約沿用）。
3. **Given** 既有手動 purge 端點，**When** 全量回歸測試，**Then** 行為零變化（30 天下限、
   四表白名單、同交易自記、PURGE 豁免如故）。

### Edge Cases

- 首跑遇歷史巨量超齡資料：單次刪除屬大交易（鎖／寫入放大）——v1 有意識接受（沿 016 單語句
  慣例）、prod 部署刀前重估批次化（見 Assumptions）。
- 手動 purge 與自動清理對同表併發：水平線刪除語意冪等、行級鎖短暫，終態一致；自記各落各的。
- 保留天數被調小後的下一輪：一次性大量刪除屬合法預期行為（同首跑情境處置）。
- 作業中途某表交易失敗：已完成之前表刪除有效（逐表獨立交易）、整體以錯誤收場不推心跳、
  下一輪重試冪等。
- dev 共用編譯資源：兩作業同輪先後跑、建置鎖自然序列化（既有慣例、無死鎖面）。
- 排程間隔與告警門檻聯動：間隔調整必同步改告警門檻（既有 2× 互錨慣例延伸至⑥）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供稽核資料自動保留期清理背景作業，覆蓋四類稽核資料源（操作日誌／
  存取軌跡／登入嘗試／會話事件），逐表刪除早於「現在－保留天數」水平線的資料列；刪除形狀
  MUST 為表白名單×天數之水平線整段刪除（構造上無挑列／任意條件路徑，島 J3）。
- **FR-002**: 每表保留天數 MUST 可經部署設定獨立調整（env 四鍵：
  `AUDIT_RETENTION_{OPERATION_LOG,ACCESS_LOG,LOGIN_ATTEMPT,SESSION_EVENT}_DAYS`）；
  設定缺席時 MUST 以 90 天為預設。
- **FR-003**: 保留天數 MUST 受 30 天下限守門（與手動 purge 同底線、不 clamp）：任一鍵在場且
  低於 30 → 作業 MUST 於開跑前整體拒絕——零刪除、結構化錯誤、非零退出、不推成功心跳。
- **FR-004**: 設定值畸形（無法解析為正整數）MUST 警示後退預設 90 照跑（沿既有背景作業
  設定容錯慣例；與 FR-003 的「明確違規」刻意不對稱——畸形＝噪音退預設、明確低於下限＝
  意圖違規零動作）。
- **FR-005**: execute 姿態每表刪除 MUST 與一筆 PURGE 操作稽核自記同交易完成（島 J3）：
  刪除筆數 0 列照落；自記列操作者 MUST 為系統身分（無人類操作者）；明細 MUST 含表名、
  保留天數、刪除筆數與作業標識（與手動 purge 列可區分）。
- **FR-006**: 操作日誌源之清理 MUST 固定豁免 PURGE 類型列（後設證據永久保留、島 J3）。
- **FR-007**: dry-run 姿態 MUST 零資料變動：回報逐表候刪數、不落任何自記、推 dry-run 心跳。
- **FR-008**: 任一表清理失敗 MUST 以結構化錯誤＋非零退出收場且不推成功心跳；已完成之表
  刪除有效（逐表獨立交易）；重複執行 MUST 冪等。
- **FR-009**: 常駐排程姿態 MUST 於既有背景回收作業同一節奏內先後執行（每輪 token 回收後
  接本作業）；排程間隔與告警門檻 MUST 維持既有 2× 互錨慣例。
- **FR-010**: 本作業與既有 token 回收作業之成功心跳 MUST 各自獨立分組（互不覆蓋）；
  升級 MUST 附一次性舊心跳分組清除步驟（防既有心跳告警因殘留序列誤紅）。
- **FR-011**: 觀測 MUST 新增成對告警：本作業心跳逾時（⑥）與 dry-run／execute 誤配（⑥b），
  鏡像既有⑤／⑤b；既有容量告警（④）退為 backstop、規則不動。
- **FR-012**: 背景作業身分之資料庫權限 MUST 最小擴張：四稽核表讀＋刪、操作日誌寫入
  （自記所需）與必要的序列使用權；MUST NOT 取得四表更新權或其他表任何權（越權操作由
  資料庫權限拒絕）。
- **FR-013**: 維運者 MUST 能以一次性手動姿態執行 dry-run 與 execute；未知作業名 MUST
  非零退出（既有 fail-loud 契約沿用）。

### Key Entities *(include if feature involves data)*

- **稽核資料四源**: 操作日誌（sys_operation_log）／存取軌跡（sys_access_log）／登入嘗試
  （sys_login_attempt）／會話事件（session_event）——皆 append-only、皆有建立時間欄與索引；
  清理僅按建立時間水平線、不觸及其他欄。
- **PURGE 自記列**: 落於操作日誌的系統清理紀錄——操作類型 PURGE、操作者空（系統身分）、
  明細（表名／天數／筆數／作業標識）；本身屬 PURGE 豁免、永久保留。
- **保留政策**: 四個部署設定鍵（每表天數）＋預設 90＋下限 30——政策本體即設定值、無新表。
- **作業心跳**: 兩背景作業各自分組的成功時戳與處理筆數序列——告警⑤／⑤b／⑥／⑥b 的判準源。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 注入超齡與線內資料後跑一輪自動清理：四表超齡列 100% 消失、線內列 100% 保留
  （機器斷言前後列集）。
- **SC-002**: 每次 execute 每表恰產生一筆 PURGE 自記（0 列照落）；自記列可辨識為系統作業
  且與手動 purge 列可區分；「刪了沒記／記了沒刪」在交易失敗注入下皆不可達。
- **SC-003**: 任一保留鍵低於下限時：四表零列被刪、作業非零退出、成功心跳缺席，且兩天內
  心跳逾時告警轉紅（fail-loud 閉環全鏈機器證）。
- **SC-004**: retention 作業停跑（心跳過期）兩天內告警⑥轉紅並投遞；僅 dry-run 心跳在場時
  ⑥b 轉紅、一次 execute 後復歸。
- **SC-005**: dry-run 前後四表與操作日誌列數零變化、回報候刪數與實際超齡列數一致。
- **SC-006**: 越權雙打全拒：作業身分對四表 UPDATE、對白名單外任一表 SELECT/INSERT 皆被
  資料庫權限拒絕。
- **SC-007**: 既有功能零回歸：手動 purge 端點全部既有驗收（下限、白名單、自記、豁免）與
  token 回收作業（心跳⑤／⑤b、dry-run／execute）既有測試零轉紅。
- **SC-008**: 升級遷移後心跳健康：清舊組＋兩作業各一輪後，⑤／⑤b／⑥／⑥b 全部處於
  正確狀態（無誤紅、無殘留序列）。

## Assumptions

### 既有資產（已核實、2026-07-21 接地偵察）

- reaper 背景作業底座（016）：`--job` 擴充位（B-100 留位）、dry-run／execute 雙姿態、
  失敗不推心跳契約、JSON 結構化 log、設定 fail-default 慣例、pushgateway 心跳＋⑤／⑤b 告警、
  sidecar loop 排程、最小權限專屬 DB 身分（m012）。
- purge 執行面（012）：四表封閉白名單、30 天下限常數、四表水平線刪除 facade（操作日誌版含
  PURGE 豁免）、同交易自記機制；憲法島 J3 為其凍結面。
- schema 面：四表皆有建立時間欄＋索引（水平線刪除走索引）；操作日誌 `created_by` 可空且
  操作者機制原生支援「無人類操作者」——系統身分表示法零 schema 變更。
- 告警④（四表容量 backstop）已在（016、B-016 搭車產物）。

### 設計取捨（有意識接受）

- 設定走 env、無管理 UI（Q1 拍板）：retention 屬 ops 政策、鮮調；調整走部署面。
- 遵憲自記（Q2 重拍）：不修憲、不走純觀測軌跡；自記累積（日 4 筆、年 ~0.5MB）可忽略。
- 前置全拒的不對稱語意（FR-003 vs FR-004）：畸形退預設照跑、明確低於下限零動作——
  「部分表照跑＋報錯」不採，設定錯誤即零動作、行為最可預測。
- 逐表獨立交易（非四表一大交易）：部分完成＋整體報錯＋下一輪冪等重試；「同交易」義務
  的射程是「單表刪除×自記」對（J3），非跨表原子性。
- 首跑／調小天數後的巨量刪除＝單語句大交易，v1 接受；prod 部署刀前重估批次化（不入本刀）。
- 觀測軌跡（JSON log＋心跳）與稽核自記雙軌並存、各司其職。

### 治理（隨刀落地）

- ADR 0076（draft→accepted 隨本刀）：遵 J3 自記＋作業身分權限擴張＋系統操作者表示法＋
  env 三分語意＋⑥/⑥b＋心跳分組遷移；`supersedes: [0075]`（「不新增任何自動刪除」
  「reaper 範圍不含 session_event」就此翻案——0075 預留條款「retention 刀再議」即本刀）。
- 憲法零 amendment（島 J3 逐條對齊、見 brainstorm §4）。
- migration（m013）＝純權限 GRANT、零表結構 DDL、零新錯誤碼、零新依賴、零新 UI。
- 收刀連帶：B-016 完成即刪；RUNBOOK §4（env 表）／§8（手動姿態命令形）／§9（心跳清組
  射程）＋pushgateway 清舊組遷移步驟。
