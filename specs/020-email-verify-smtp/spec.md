- Q: 發碼端點要不要圖形驗證碼前置？ → A: **加 captcha 前置**（user 親決、否決「不加」推薦案）——複用 007 無狀態簽題範式另立自助語境題（challenge 綁定操作者、提交即消耗、答案不可自題還原）；發碼請求附答案、缺／錯／過期／重放→明確拒因且零寄信、不計冷卻與日上限、答錯 UI 自動換題；僅發碼端點受此閘（驗證提交與解除綁定不受）。
- Q: admin 端要不要同步建立信箱格式守門？ → A: **加、且不設「值未變豁免」**（user 自訂案、否決「本刀不加」推薦案與「加＋豁免」案）——admin 建帳／改資料與自助發碼共用單一格式守門；重送既存怪值同樣被擋＝存量怪值於下次觸及時被迫修正或清空（拒因明確指向信箱格式、修正欄位在同一表單內＝自癒動線）；空值（未綁定）不受守門。
- Q: 重發冷卻倒數在頁面重整後的重建策略？ → A: **純前端倒數＋冷卻拒因攜剩餘秒數兜底**（照推薦案）——重整後倒數消失、鈕可按；仍在冷卻時後端拒因攜剩餘秒數（015 冷卻拒因先例同型）、前端據此重建倒數；零額外查詢端點、零持久化。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 本人綁定／變更信箱並完成驗證 (Priority: P1)

已登入會員在個人中心信箱卡輸入新信箱、填妥圖形驗證碼、按「發送驗證碼」：新信箱收到一封含六位數字碼的驗證信（有效期 10 分鐘），畫面進入回填態並顯示重發冷卻倒數；**此時庫中信箱與驗證態完全未變**。會員回填正確碼提交後，新信箱**一步寫入**並呈「已驗證」徽章（含驗證時刻）；回填錯誤碼得到明確拒因、同一憑據錯滿 3 次即作廢需重新發碼。對 admin 代填的現值信箱同樣可直接發碼驗證。

**Why this priority**: B-028 信箱半邊本體；「驗證即提交」＝本刀核心語意（庫中 email 三態：空／admin 代填／已驗證，無佔位窗口）。

**Independent Test**: dev 棧會員對新信箱發碼→自開發收信服務取信抽碼→回填提交→DB 斷言信箱已更新＋驗證記錄在＋稽核一筆；錯碼三次→憑據作廢。

**Acceptance Scenarios**:

1. **Given** 已登入會員於信箱卡輸入格式合法的新信箱並答對圖形驗證碼，**When** 按「發送驗證碼」，**Then** 該新信箱收到含六位碼與有效期說明的驗證信、畫面進入回填態＋冷卻倒數；庫中信箱與驗證態不變。
1a. **Given** 圖形驗證碼缺失、答錯、過期或重放，**When** 送出發碼請求，**Then** 明確拒因、零寄信、不計冷卻與日上限；介面自動換新題（該題已消耗）。
2. **Given** 已收到驗證碼，**When** 回填正確碼提交，**Then** 信箱一步寫入＋呈已驗證徽章（含時刻）；操作稽核落一筆（前後值、操作者本人）。
3. **Given** 回填錯誤碼，**When** 提交，**Then** 明確拒因、庫不變；同一憑據累計錯 3 次後作廢，再提交（含正確碼）一律拒、須重新發碼。
4. **Given** 憑據逾有效期（10 分鐘），**When** 提交，**Then** 過期拒因；庫不變。
5. **Given** 另一活性帳號已持有同一信箱（含大小寫變體），**When** 本人發碼或提交，**Then** 於預檢與終判皆得明確「已被使用」拒因。
6. **Given** 發送驗證碼後放棄（關頁、不回填），**Then** 庫零殘留；原信箱與其驗證態不變。
7. **Given** 已成功消耗的憑據或他帳號的憑據，**When** 重放提交，**Then** 一律拒（單次性＋操作者綁定）。
8. **Given** admin 曾代填信箱（未驗證），**When** 會員對該現值發碼並完成驗證，**Then** 現值轉為已驗證（值不變、驗證態新增）。
9. **Given** 會員已綁定信箱（不論驗證與否），**When** 於信箱卡按「解除綁定」並確認，**Then** 信箱清空、呈未綁定態；操作稽核落一筆（前後值）；驗證記錄留存（日後填回曾驗值依導出語意恢復已驗證）。
10. **Given** 會員未綁定信箱，**When** 直接以工具呼叫解除綁定，**Then** 明確拒因（無可解除）；介面上該鈕於未綁定時不顯示。

### User Story 2 - admin 端語意與驗證態呈現 (Priority: P2)

管理員在使用者管理建帳或修改資料時照常可填寫信箱，但**填寫恆不產生已驗證態**；修改已驗證會員的信箱後，該會員的驗證態自動呈未驗證；改回曾驗證過的舊值則自動恢復已驗證（擁有權證明事件確實發生過）。管理員填寫與其他活性帳號重複的信箱時得到明確拒因。

**Why this priority**: D4／D9 語意的管理面兌現；SSO（下一刀）以已驗證信箱對映帳號的前提。

**Independent Test**: admin 改某已驗證會員信箱→該會員個人中心呈未驗證；改回原值→恢復已驗證；admin 對另一帳號填入同一信箱→明確拒因。

**Acceptance Scenarios**:

1. **Given** admin 建帳時填寫信箱，**When** 該會員登入看個人中心，**Then** 呈未驗證（可對現值直接發碼補驗）。
2. **Given** 會員信箱已驗證，**When** admin 修改其信箱為新值，**Then** 會員側呈未驗證；op-log 有 admin 改值軌跡。
3. **Given** 前項後，**When** admin 將信箱改回原已驗證值，**Then** 自動恢復已驗證（驗證時刻為原次）。
4. **Given** 某活性帳號已持有信箱 X（不論驗證與否），**When** admin 對另一帳號填入 X 或其大小寫變體，**Then** 明確業務拒因（非內部錯誤）、零寫入。
5. **Given** 會員被軟刪，**When** admin 對他帳號填入被刪者曾持有的信箱，**Then** 成功（軟刪不佔用唯一額度）。
6. **Given** admin 建帳或改資料填入格式不合法的信箱，**When** 送出，**Then** 明確拒因（指向信箱格式）、零寫入；清空（空值）不受格式守門。
7. **Given** 某會員存有守門上線前的歷史怪值信箱，**When** admin 編輯該會員任何資料（表單整包重送含原怪值），**Then** 同樣被格式拒因擋下（無「值未變豁免」）；admin 於同一表單修正或清空信箱後重送成功。

### User Story 3 - 節流與濫用防護 (Priority: P3)

同一會員發送驗證碼後 60 秒內再發被明確拒因拒絕（介面同步顯示倒數）；單一會員每日發送上限 10 次，超限拒絕。快取基建不可用時，發碼與驗證提交一律安全拒絕（fail-closed）並發降級告警，絕不靜默放行。

**Why this priority**: 防濫用＋護寄信配額（Gmail 2000 封/日）；獨立可測。

**Independent Test**: 連續兩次發碼（間隔小於 60s）→第二次拒；當日第 11 次發碼→拒；停快取服務→發碼與提交皆明確拒＋降級告警。

**Acceptance Scenarios**:

1. **Given** 剛成功發送驗證碼，**When** 60 秒內對任一信箱再發（含重整頁面後誤按），**Then** 明確拒因**攜剩餘秒數**、前端據此重建倒數；滿 60 秒後重試成功。
2. **Given** 當日已成功發送 10 次，**When** 第 11 次發送，**Then** 明確拒因；次日恢復。
3. **Given** 快取基建不可用，**When** 發碼或提交驗證，**Then** 明確錯誤拒絕（不寄信、不寫庫）＋結構化降級告警；快取恢復後功能自癒。
4. **Given** 發碼因節流被拒，**When** 檢視寄信面，**Then** 零寄出（拒絕先於寄信）。

### User Story 4 - 介面三語化 (Priority: P4)

本刀全部新介面文字（信箱卡新動線、已驗證徽章、各拒因提示）支援 zh-TW／zh-CN／en-US 三語、切語系零 raw key；zh-TW 為在地化正體用語。

**Why this priority**: rev4 三語紀律例行兌現；獨立可驗。

**Independent Test**: 三語系各切一次走完 US1 全流程，零 raw key。

**Acceptance Scenarios**:

1. **Given** 語系 en-US，**When** 走完發碼→錯碼→過期→成功全流程，**Then** 全部提示為英文、零 raw key。
2. **Given** 語系 zh-TW，**When** 開信箱卡與已驗證徽章，**Then** 用語為在地化正體。

### Edge Cases

- 同會員兩瀏覽器並行對不同新信箱各發一碼→兩憑據皆有效（無狀態）、先後成功者依序覆寫（皆已證明擁有權、終態＝最後成功值）；同信箱被兩帳號競驗→唯一性終判序列化裁決、後到者明確拒。
- 驗證期間 admin 改了該會員信箱→憑據仍綁發碼時的新信箱、提交成功照寫入（本人擁有權證明優先；op-log 兩筆軌跡俱在）。
- 驗證期間會員被停用／軟刪／踢除→提交於序列化鎖內重驗標的活性（島 I 範式）、拒絕不寫入。
- 寄信逾時或 SMTP 故障→發碼明確失敗、不回傳憑據、不計入冷卻與日上限（失敗不佔額度）；提示不洩內部細節。
- 信箱格式邊界：前後空白 MUST trim；超長輸入被形制上限擋；大小寫變體視為同一信箱（唯一性與比對一致）。
- 對「與現值相同且已驗證」的信箱再發碼→允許（重驗無害、刷新驗證時刻）；介面可誠實顯示已驗證現狀。
- 主旨後綴設定為空→主旨照常組裝（無後綴）；寄件顯示名含非 ASCII（中文）→信件標頭正確編碼。
- 收信服務（dev）清空與多信箱並存→E2E 以收件人條件取信、不誤抓他測試殘留。
- 頁面重整後冷卻倒數消失→重發鈕可按、後端節流權威拒絕＋拒因攜剩餘秒數、前端重建倒數（體驗劣化上限＝一次誤按）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供登入者本人「對指定新信箱發送驗證碼」能力：輸入 MUST 經圖形驗證碼查驗（FR-018）→ 格式驗證（FR-019 單一守門）→ 唯一性預檢（他活性帳號已持有（大小寫不敏感）→明確拒因）→ 節流檢查 → 產生六位數字碼 → 寄出驗證信 → 回傳驗證憑據。任一步失敗 MUST 明確拒因且 MUST NOT 外洩憑據；失敗 MUST NOT 計入冷卻與日上限。
- **FR-002**: 驗證憑據 MUST 為伺服器簽章之無狀態短效載體：綁定操作者、標的新信箱、有效期 10 分鐘、單次性識別；驗證碼 MUST NOT 可自憑據還原（密碼學單向）；簽章金鑰 MUST 與既有各金鑰隔離（獨立一把）。發碼與憑據簽發 MUST 零庫面寫入。
- **FR-003**: 驗證提交 MUST 依序：驗簽章／有效期／操作者綁定 → 嘗試次數檢查（同一憑據上限 3 次、超限作廢）→ 碼比對 → 成功後於**同一原子操作**內：寫入新信箱至使用者資料＋刷新信箱驗證記錄＋落操作稽核（前後值、操作者本人）；寫入 MUST 沿使用者域統一序列化鎖並於鎖內重驗標的活性與唯一性終判（lock-then-redecide，島 I1／I2 範式）。
- **FR-004**: 驗證即提交不變式：新信箱於驗證成功前 MUST NOT 以任何形式寫入庫（無 pending 欄／列）；驗證失敗、過期、憑據作廢、使用者放棄 MUST 零庫面殘留。
- **FR-005**: 驗證成功 MUST 使該憑據永久失效（重放 MUST 拒）；他帳號憑據提交 MUST 拒（操作者綁定）。
- **FR-006**: 活性帳號信箱 MUST 唯一（大小寫不敏感相等；未填不受限、軟刪帳號不佔用）；唯一性由資料庫層約束背書；自助流於預檢與終判兩處攔截；admin 建帳／改資料寫入重複值 MUST 得到明確業務拒因（非內部錯誤）。
- **FR-007**: 信箱「已驗證」MUST 為導出語意＝現行信箱值與驗證記錄之比對（大小寫不敏感）：admin 填寫／修改 MUST NOT 產生已驗證態；改值即失配呈未驗證；改回曾驗證值即恢復已驗證。驗證記錄 MUST 每使用者至多一筆（重驗刷新）、記錄驗過的值與驗證時刻、不存狀態欄；判定 MUST 收斂為單一純函式 seam 各處共用。
- **FR-008**: 自助資料更新（updateProfile）MUST 結構性不再受理信箱欄（自 DTO 移除）；自助信箱寫入僅兩路徑＝驗證提交（FR-003、換值）與解除綁定（FR-017、清空）。既有其他欄位（暱稱／性別／電話）行為 MUST 零改動。
- **FR-009**: 登入者 profile 讀取 MUST 含信箱驗證態投影（驗證時刻或空）；個人中心信箱卡 MUST 呈現已驗證徽章（含時刻）與新動線（發碼→冷卻倒數→回填→提交），獨立儲存鈕退場。
- **FR-010**: 發碼節流 MUST：同一操作者距上次成功發送未滿 60 秒再發→明確拒因**且攜剩餘秒數**（前端據此重建倒數；倒數本身純前端、不設查詢端點與持久化）；同一操作者單日成功發送上限 10 次（拒因不攜秒數）；節流判定 MUST 先於寄信（被拒＝零寄出）。快取基建不可用→發碼與提交 MUST fail-closed（明確錯誤、不寄信、不寫庫）且 MUST 發結構化降級告警；常數 MUST 為程式內固定值（不入系統設定）。
- **FR-011**: 驗證信 MUST 經 SMTP 寄出：純文字、含六位碼與有效期說明、主旨帶可設定後綴、寄件身分（寄件地址／顯示名／Reply-To）可設定；寄送 MUST 有逾時上限、逾時或故障→明確拒因。寄送身分與連線參數 MUST 為部署級靜態設定；正式環境 MUST 加密傳輸不可降級＋伺服器憑證驗證；開發環境 MAY 明文對開發收信服務。
- **FR-012**: SMTP 密碼與憑據簽章金鑰 MUST 循既有機密管線（密文入版控、明文不入 repo、佈署預檢涵蓋、洩漏掃描防線生效）；SMTP 密碼 MUST NOT 出現於日誌／回應／稽核。
- **FR-013**: 開發棧 MUST 含可機器查詢信件內容之收信服務（E2E 斷言「信寄達＋內含碼＋碼可完成驗證」）；正式部署形 MUST 零收信服務痕跡。
- **FR-014**: 本刀全部新介面文字 MUST 三語支援（zh-TW 在地化正體）、切語系零 raw key；wire 拒因 msg MUST 為穩定 `backend.*` 家族 i18n key、錯誤碼 reuse `2222` 家族零新碼、回應信封與契約機器化紀律照走。
- **FR-015**: 驗證碼明文 MUST NOT 出現於伺服器日誌、操作稽核 payload、任何 API 回應（發碼回應僅含憑據）；憑據內容 MUST NOT 使碼可離線還原（同 FR-002）。
- **FR-016**: base-web 改動 MUST 遵循 fork-delta 紀律（本刀預期全我方新檔／新增型圈界；如涉上游既有行則修改型帶原行標記）。
- **FR-017**: 系統 MUST 提供登入者本人「解除信箱綁定」能力：確認後將信箱清空（呈未綁定）；寫入 MUST 沿使用者域統一序列化鎖＋同一原子操作落操作稽核（前後值、操作者本人）；驗證記錄 MUST 留存不動（清空＝比對失配呈未驗證、非刪除驗證史）；未綁定時呼叫 MUST 明確拒因；本動作無寄信、MUST NOT 要求驗證碼或圖形驗證碼、不計入發碼節流；介面於未綁定時 MUST 不顯示該動作。
- **FR-018**: 發碼請求 MUST 附有效圖形驗證碼答案：challenge MUST 綁定操作者、提交即消耗（單次標記先於答案比對）、答案 MUST NOT 可自 challenge 本身還原（沿 007 簽題語意、另立自助語境、獨立於 login 節流閘）；缺失／答錯／過期／重放 MUST 明確拒因且零寄信、MUST NOT 計入冷卻與日上限；答錯後介面 MUST 自動換新題。驗證提交（FR-003）與解除綁定（FR-017）MUST NOT 受此閘。
- **FR-019**: 信箱格式守門 MUST 為單一驗證點（trim、基本信箱形、長度上限），自助發碼與 admin 建帳／改資料共用零分叉；admin 寫入不合法格式 MUST 明確拒因（指向信箱格式、非內部錯誤），**無「值未變豁免」**——重送既存怪值同樣被擋（存量怪值於下次觸及時被迫修正或清空）；空值（未綁定／清空）MUST NOT 受格式守門。

### Key Entities *(include if feature involves data)*

- **信箱驗證記錄**: 每使用者至多一筆的狀態事實——驗過的信箱值（原樣保存）、最後驗證時刻、首建時刻與首建操作者（成對、首建後不動）；「已驗證」恆由現行信箱值比對導出、不存狀態欄；重驗刷新值與時刻。
- **驗證憑據**: 無狀態短效簽章載體——操作者、標的新信箱、有效期、單次性識別、碼之單向摘要；不落庫；嘗試計數與消耗標記由快取層承載。
- **SMTP 寄送設定組**: 部署級靜態設定——連線（主機／埠／加密模式／帳號）＋寄件身分（寄件地址／顯示名／Reply-To／主旨後綴）＋密碼（機密管線）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: dev 棧端對端：發碼→收信服務取信抽碼→回填提交→信箱更新＋已驗證呈現，全流程自動化走通率 100%；驗證信內容含六位碼且該碼可完成驗證。
- **SC-002**: 濫用防護：同一憑據錯 3 次後提交成功率 0%（含其後正確碼）；過期憑據成功率 0%；已成功憑據重放成功率 0%；跨帳號憑據成功率 0%。
- **SC-003**: 節流與前置閘：冷卻窗內重發被拒率 100%；單日第 11 次發送被拒率 100%；無效圖形驗證碼（缺／錯／過期／重放）之發碼被拒率 100% 且零寄出、零額度消耗；快取不可用時發碼／提交被安全拒絕率 100%（零寄信、零寫庫）且降級告警有觀測背書。
- **SC-004**: 唯一性與格式：對他活性帳號已持有信箱（含大小寫變體）之驗證於終判被拒率 100%；admin 端寫入重複值或不合法格式值得到明確業務拒因率 100%（含重送既存怪值）；未驗證值佔用唯一額度的自助路徑數＝0（updateProfile 無信箱欄有契約級斷言）。
- **SC-005**: 導出語意：admin 改信箱後會員側呈未驗證率 100%；改回曾驗證值自動恢復率 100%；判定三態（無記錄／匹配／失配）各有自動化測試背書。
- **SC-006**: 三語切換下本刀全部新介面零 raw key。
- **SC-007**: 洩漏面：驗證碼明文於日誌／稽核／API 回應出現件數 0；新增機密經三層洩漏掃描 0 命中；SMTP 密碼於日誌／回應出現件數 0。
- **SC-008**: 部署形：正式 compose 形零收信服務痕跡；正式 TLS 形不可降級有測試背書（加密模式建構兩態單元測試）。
