## Clarifications

### Session 2026-07-12

- Q: 角色「預設首頁」與選單授權不一致時怎麼辦？（改首頁、撤選單、刪角色重建都能一鍵造成「首頁指向該角色看不見的頁」→ 該角色使用者登入直接落 404） → A: C 讀端兜底——寫端不設限（首頁候選維持頁面全集、沿模板語意）；系統於下發使用者路由時驗證首頁是否在該使用者可見樹內，不在→落點改為可見樹第一個可導航頁（可見樹全空才維持預設值）。404 一類整個消失，含既有壞資料與一切間接成因。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理者能管理角色的完整生命週期 (Priority: P1)

超級管理員在角色管理頁檢視分頁角色列表（依名稱模糊、代碼模糊、狀態等值過濾），新增角色（零授權起步）、編輯角色（名稱／描述／狀態可改，代碼恆不可變），以及刪除角色（單筆與批次）。刪除受三層守門保護（種子角色不可刪、掛有使用者指派不可刪、操作者自身所屬角色不可刪），過門的刪除為軟刪除，且同一交易將該角色的全部授權移入歸檔——同代碼日後重建的新角色不繼承任何舊授權。

**Why this priority**: 這是頁面的基本價值，也是其餘所有故事的載體。管理面家族第一刀的 MVP：沒有角色生命週期，授權治理無物可治。刪除連動歸檔是本故事最重的安全語意——它封死「代碼重用導致靜默繼承舊授權」的破口。

**Independent Test**: 不需要任何授權面板即可完整驗證——新增→查詢→編輯→刪除全鏈走通；守門矩陣（種子／掛載中／自身角色×單筆／批次）逐案驗證；刪除後以同代碼重建、驗證新角色授權全空。

**Acceptance Scenarios**:

1. **Given** 系統已有若干角色，**When** 以名稱模糊＋狀態條件查詢，**Then** 列表回符合條件的分頁結果，欄位含名稱、代碼、描述、狀態與建立／更新資訊，預設以建立順序排列。
2. **Given** 新增表單，**When** 提交合法的名稱／代碼／描述／狀態，**Then** 建立成功，且新角色的三維授權（選單／按鈕／端點）全部為空——一切授權須經治理面板顯式下放。
3. **Given** 已存在活性代碼 X 的角色，**When** 以代碼 X 新增，**Then** 回業務衝突與專屬訊息；**Given** 代碼 X 的角色已被刪除，**When** 以代碼 X 新增，**Then** 成功（代碼可重用）。
4. **Given** 編輯表單，**When** 嘗試變更角色代碼，**Then** 被拒絕並回專屬訊息（代碼不可變）。
5. **Given** 編輯請求未攜帶任何欄位變更，**When** 提交，**Then** 系統提前判定無作用：不更動任何時戳、不落操作稽核。
6. **Given** 三個種子角色之一，**When** 刪除，**Then** 被拒絕（種子角色保護）。
7. **Given** 掛有使用者指派的角色，**When** 刪除，**Then** 被拒絕，且拒絕訊息含實際掛載人數。
8. **Given** 操作者自身所屬的角色，**When** 刪除，**Then** 被拒絕（防自鎖）。
9. **Given** 批次刪除清單中任一項違反守門，**When** 提交批次，**Then** 整批拒絕、資料零變更（不可部分成功）。
10. **Given** 通過全部守門的角色，**When** 刪除成功，**Then** 該角色為軟刪除，且其全部授權（含受保護列）於同一交易移入歸檔、標記來源＝角色刪除、記錄來源角色識別；操作稽核同交易落地。
11. **Given** 已刪除的角色，**Then** 系統不提供「復原角色」能力（刪除單向）；歸檔中來源＝角色刪除的授權列不可經回收桶手動復原。

### User Story 2 - 管理者能對角色下放與回收三個維度的授權 (Priority: P2)

超級管理員對任一角色開啟三個授權面板——選單可見性、頁內按鈕、API 端點——勾選該維度的期望全集後提交。系統以「全量替換」語意落地：與現況比對導出撤銷集與新授集，撤銷的授權移入歸檔（可自回收桶復原）、新授的授權立即建立。若撤銷集觸及受保護授權，整批拒絕、零變更。

**Why this priority**: 授權治理寫端是整個管理面家族的權力核心——user／menu 頁的授權語意都建立在它之上。本刀先立治理狀態機，家族後續刀只消費、不重設計。

**Independent Test**: 對一個測試角色逐面板執行「開啟→勾選→提交→重開驗回讀」；構造含受保護項的撤銷提交驗證整批拒；以受影響帳號實際登入驗證授權收縮／擴張。

**Acceptance Scenarios**:

1. **Given** 選單授權面板，**When** 開啟，**Then** 呈現活性選單全集的樹狀候選與該角色現況勾選；提交新勾選全集後重開面板，回讀與提交一致。
2. **Given** 按鈕授權面板，**When** 開啟，**Then** 候選清單＝活性選單所登記按鈕代碼的聯集（去重）；端點授權面板候選清單＝系統路由登記表中受政策管制端點的全集（路徑×方法、依路徑群組呈現、支援群組級勾選）——兩者皆與授權判定面同源，不多列、不漏列。
3. **Given** 提交的期望全集與現況完全相同，**When** 提交，**Then** 回報成功（空差異亦為合法提交）。
4. **Given** 提交的撤銷集含受保護授權，**When** 提交，**Then** 整批拒絕、資料零變更（於任何寫入發生之前判定），回業務錯誤與明細（被擋目標清單）。
5. **Given** 撤銷若干非保護授權並新授若干項，**When** 提交成功，**Then** 被撤銷的授權出現在回收桶（含快照與來源角色識別）、新授的授權立即參與判定。
6. **Given** 某使用者所屬角色的 API 端點授權被回收，**When** 該使用者發出下一個該端點請求，**Then** 被以既有的「權限不足」語意拒絕（API 授權即時生效）；其選單／按鈕顯隱於下次載入更新（明文語意、不做推播）。
7. **Given** 選單勾選全集中含已失效的選單項，**When** 提交，**Then** 該項被跳過、不產生孤兒授權，其餘正常落地。
8. **Given** 同一角色上授權提交與角色刪除併發，**When** 兩者交錯執行，**Then** 結果等價於某一種先後序列——不出現「角色已刪除但新授權殘留」的中間態。

### User Story 3 - 停用角色即時收回其授權 (Priority: P3)

超級管理員將角色狀態改為停用後，該角色即不再參與授權判定：其成員的 API 判定、選單可見性、按鈕能力集均不再計入該角色。停用可逆——重新啟用即恢復，停用期間使用者-角色指派資料保留不動。

**Why this priority**: 停用是「暫時斷權」的正規手段（相對於刪除的永久性）。現況停用僅是顯示狀態、不影響授權——名實不符是潛在安全缺口。依賴 US1（狀態編輯入口），不依賴授權面板。

**Independent Test**: 準備僅掛單一角色的測試帳號，停用該角色後驗證其受管制請求被拒、重新載入後選單收縮；重新啟用後驗證恢復。

**Acceptance Scenarios**:

1. **Given** 某使用者僅屬於角色 A（啟用中），**When** 管理者停用 A，**Then** 該使用者自下一請求起，受管制端點被以「權限不足」語意拒絕；前端重新載入後選單／按鈕收縮。
2. **Given** 使用者屬於角色 A 與 B，**When** 停用 A，**Then** 其有效授權縮為 B 單獨的授權集（聯集縮小、不歸零）。
3. **Given** 操作者自身所屬的角色，**When** 嘗試停用，**Then** 被拒絕並回專屬訊息（防自鎖）。
4. **Given** 超級管理員角色，**When** 任何人嘗試停用，**Then** 被拒絕（恆禁停用的結構護欄）。
5. **Given** 已停用的角色，**Then** 供指派消費的「全量角色」查詢不含該角色；重新啟用後恢復出現。
6. **Given** 停用後重新啟用，**Then** 該角色成員的授權完整恢復（指派與授權資料在停用期間未被變更）。

### User Story 4 - 管理者能檢視授權回收桶並復原誤撤的授權 (Priority: P4)

超級管理員在回收桶頁檢視被撤銷的授權（分頁；可依來源角色與維度過濾），每列附系統判定的「可復原」旗標。可復原的列一鍵復原——授權回到現役、歸檔列移除；不可復原的列（角色刪除連動、或同代碼角色已是不同實例）顯示為停用態且後端拒絕復原。

**Why this priority**: 回收桶是「撤銷必歸檔」語意的消費端——沒有它，誤撤救援只能靠直接操作資料，治理閉環不成立。依賴 US1／US2 產生歸檔資料。

**Independent Test**: 經授權面板撤銷若干授權後，於回收桶驗證列表、過濾、復原三態；刪除角色後以同代碼重建，驗證舊歸檔列不可復原。

**Acceptance Scenarios**:

1. **Given** 回收桶頁，**When** 開啟，**Then** 分頁列表以歸檔時間新到舊排列，支援「來源角色」與「維度」（選單／按鈕／端點，由歸檔列內容推導）兩條件過濾。
2. **Given** 任一歸檔列，**Then** 其「可復原」旗標由後端判定並隨列下發，前端不自行以原因字面推斷；旗標為否的列呈現停用態。
3. **Given** 一條可復原的歸檔列，**When** 復原，**Then** 該授權回到現役、歸檔列移除、操作稽核落地；受影響角色的成員自下一請求起恢復該授權。
4. **Given** 歸檔列對應的授權已存在於現役，**When** 復原，**Then** 回報成功（無作用），歸檔列仍被消費移除。
5. **Given** 來源＝角色刪除的歸檔列、或同代碼角色已為重建的新實例，**When** 強行對後端發出復原請求，**Then** 被拒絕並回專屬訊息（縱深防禦——不只靠前端隱藏）。
6. **Given** 選單維歸檔列的標的選單已失效，**When** 復原，**Then** 被拒絕（不灌無效授權）。
7. **Given** 不存在的歸檔識別，**When** 復原，**Then** 回業務錯誤（不靜默）。
8. **Given** 回收桶頁的選單項，**Then** 三種語言的選單譯文完整呈現（不出現原始鍵字面）。

### User Story 5 - 拒絕原因帶具體明細 (Priority: P5)

管理操作被系統拒絕時（刪除守門、受保護撤銷、停用自鎖、代碼衝突、不可復原……），操作者看到的訊息不再是泛化的「操作失敗」，而是專屬原因＋具體明細——例如「該角色掛有 3 個使用者，不可刪除」、受保護撤銷列出被擋的具體目標。

**Why this priority**: 治理守門愈多，泛化訊息的挫折感愈重；具體明細讓操作者自助排除、不需查後台。依賴前四個故事產生的拒絕場景。

**Independent Test**: 逐一觸發各拒絕場景，驗證訊息含正確插值（人數、目標清單）且三語齊備。

**Acceptance Scenarios**:

1. **Given** 掛有 3 個使用者的角色，**When** 刪除被拒，**Then** 介面訊息呈現實際人數（如「該角色掛有 3 個使用者」），非泛化訊息。
2. **Given** 受保護撤銷被整批拒絕，**When** 檢視錯誤，**Then** 明細列出被擋的目標與所屬維度。
3. **Given** 既有功能的無明細業務錯誤路徑，**Then** 其行為與訊息完全不受本刀影響（零改動）。
4. **Given** 任一新拒因訊息，**Then** 三種語言的譯文（含插值位）齊備。

### User Story 6 - 每個角色有可管理的預設首頁 (Priority: P6)

超級管理員可檢視並變更任一角色的預設首頁（登入後的落點頁）。候選選項為系統頁面全集；變更後該角色成員自下次載入起落在新首頁。首頁與選單授權的一致性不在寫端強制——系統在下發使用者路由時兜底（首頁不可見→落點改為第一個可導航頁），管理者無論如何設定都不會把使用者送進 404。

**Why this priority**: 首頁選擇器是頁面模板既有的可見控件——不接線它就是一個「切了彈回」的靜默死控件。價值輕、風險低，排最後。

**Independent Test**: 變更測試角色的預設首頁，以該角色帳號重新登入驗證落點。

**Acceptance Scenarios**:

1. **Given** 授權面板中的首頁選擇器，**When** 開啟，**Then** 呈現該角色現值與頁面全集候選。
2. **Given** 選定新首頁並提交，**When** 該角色成員下次登入或重新載入，**Then** 落點為新首頁。
3. **Given** 首頁變更，**Then** 與操作稽核同交易落地。
4. **Given** 角色的預設首頁指向其不可見的頁面（不論由改首頁、撤選單或刪角色重建造成），**When** 該角色成員登入或重新載入，**Then** 落點為其可見選單中的第一個可導航頁（不落 404）；**Given** 其可見選單全空，**Then** 落點維持預設值（空授權角落、誠實呈現）。

### Edge Cases

- **批次刪除含一項違規**：整批拒絕、零變更——不存在「刪掉一半」的中間態。
- **代碼重用**：活性代碼重複→衝突；已刪代碼重用→允許，且新角色不繼承任何舊授權（連動歸檔＋同實例判定雙重封死）。
- **全空編輯**：提前無作用——時戳不動、稽核不落（避免「無變更卻留下變更痕跡」的假訊號）。
- **空差異提交**：期望全集＝現況→成功；判定面同步照常執行（刻意不優化、行為可預期）。
- **受保護項混入大批撤銷**：整批拒＋明細——不做「跳過保護項、其餘照做」的部分成功。
- **勾選集含失效選單項**：跳過不落列，其餘正常（不因一項失效整批失敗，也不產生孤兒授權）。
- **授權提交與角色刪除併發**：互斥序列化——不出現刪除後殘留新授權。
- **授權復原與角色刪除／停用併發**（對抗式審查 Blocker 1）：復原亦納入鎖序、鎖內重驗可復原（角色活性＋同實例）——不出現「復原的授權逃過刪除連動歸檔而殘留、被同代碼重建角色靜默繼承」；無鎖預讀判 restorable 後才寫入的路徑不存在。
- **判定面同步（重載）失敗**（對抗式審查 Blocker 2）：授權真相已提交而同步失敗時，保留上一份已知良好判定面、不空窗、告警、有界重試——不發生「同步一失敗即清空判定面→全體角色含超管全域鎖死、救援端點亦失效、唯重啟可救」。
- **同代碼重建後開回收桶**：舊實例的歸檔列全部不可復原（旗標為否＋後端拒）。
- **復原標的已在現役**：成功（無作用）、歸檔列照樣消費移除。
- **同一授權反覆撤銷**：回收桶累積多列歷史屬預期；任一列復原後其餘列變為「已在現役」的無作用路徑。
- **停用多角色使用者的其中一角色**：有效授權為剩餘啟用角色的聯集（不歸零）。
- **停用與「全量角色」查詢**：停用角色不出現在指派候選中。
- **歷史歸檔列無來源角色識別**（本刀結構變更前產生者）：一律判不可復原（誠實退化、不猜測）。
- **管理者停用／刪除自己所屬角色**：雙路自鎖防護皆拒。
- **新角色初始狀態**：三維授權全空、面板全不勾選——顯式下放才有授權。
- **首頁指向不可見頁**：不論成因（改首頁、撤選單、刪角色重建、歷史資料），登入落點由讀端兜底至可見樹第一個可導航頁——「登入落 404」不可達；可見樹全空（如使用者的角色全被停用）時維持預設落點值、選單空白誠實呈現。

## Requirements *(mandatory)*

### Functional Requirements

#### 角色查詢（US1）

- **FR-001**: 角色列表 MUST 分頁，MUST 支援名稱模糊、代碼模糊、狀態等值三條件過濾；預設以建立順序排列（列表排序參數掛載不屬本刀）。
- **FR-002**: 「全量角色」查詢 MUST 只回傳活性且啟用中的角色（供使用者指派等下游消費），內容含識別、名稱、代碼。
- **FR-003**: 本刀全部能力的存取授權 MUST 沿用既有政策基線（已預埋、不變更授權矩陣）；各能力對外註冊的方法動詞 MUST 與預埋政策逐條一致。

#### 角色建立與編輯（US1）

- **FR-004**: 新增 MUST 接受名稱、代碼、描述、狀態；代碼 MUST 通過形制守門——非空、僅限英文字母／數字／底線、長度 1~64（防止代碼字面破壞授權資料的欄位邊界）；與現存活性代碼重複 MUST 回業務衝突與專屬訊息。
- **FR-005**: 新角色 MUST 以零授權起步（三維全空）；系統 MUST NOT 給新角色任何隱含預設授權。
- **FR-006**: 角色代碼 MUST 不可變——編輯請求試圖變更代碼 MUST 被拒（專屬訊息）。（授權、歸檔、指派皆以代碼與識別錨定；允許改碼將撕裂全部對應。）
- **FR-007**: 編輯 MUST 可改名稱、描述、狀態；請求未攜帶任何欄位變更時 MUST 提前判定無作用（不更動時戳、不落操作稽核）；描述送空字串＝清空。
- **FR-008**: 編輯將狀態改為停用時 MUST 通過停用守門（FR-014、FR-015）。

#### 角色刪除（US1）

- **FR-009**: 刪除 MUST 依固定順序通過三層守門：①種子角色不可刪 → ②掛有使用者指派不可刪（拒絕明細含掛載人數）→ ③操作者自身所屬角色不可刪。任一層擋下 MUST 回業務錯誤、零變更。
- **FR-010**: 批次刪除 MUST 逐項驗證、任一項違規則整批拒絕零變更（不可部分成功）；整個批次 MUST 於單一交易內完成。
- **FR-011**: 通過守門的刪除 MUST 為軟刪除，且 MUST 於同一交易將該角色的全部授權（含受保護列——角色將消失，保護語意不適用）移入歸檔：原授權內容快照、來源標記＝角色刪除、記錄來源角色識別；操作稽核同交易落地。
- **FR-012**: 角色刪除 MUST 單向：系統 MUST NOT 提供已刪角色的復原能力；歸檔中來源＝角色刪除之列 MUST NOT 可手動復原；同代碼新建的角色 MUST NOT 以任何路徑繼承舊實例的授權。

#### 停用即斷權（US3）

- **FR-013**: 停用中的角色 MUST 不參與授權判定——其成員的 API 判定、選單可見性、按鈕能力集 MUST 均不計入該角色；API 面 MUST 自下一請求起生效。
- **FR-014**: 操作者 MUST NOT 能停用自己所屬的角色（防自鎖；專屬訊息）。
- **FR-015**: 超級管理員角色 MUST 恆禁停用——不因操作者身分而異（結構護欄：即使日後管理能力下放，此防線仍在）。
- **FR-016**: 停用 MUST 可逆：重新啟用後授權即恢復；停用期間使用者-角色指派與授權資料 MUST 保留不動。

#### 授權治理狀態機（US2）

- **FR-017**: 三維授權寫入 MUST 以「期望全集」為輸入，由系統與現況比對導出撤銷集與新授集（全量替換語意）；MUST NOT 提供增量式寫入介面。
- **FR-018**: 撤銷集觸及受保護授權時 MUST 整批拒絕、零變更（於任何寫入發生之前判定），回業務錯誤與被擋目標明細；一般管理介面 MUST NOT 提供設定／解除保護旗標的能力（防鎖死，by-design）。
- **FR-019**: 撤銷 MUST 為「移入歸檔」——原授權內容完整快照＋來源角色識別＋撤銷類來源標記；新授 MUST 補齊治理欄位（非保護、建立時間與操作者）。
- **FR-020**: 授權的持久化儲存 MUST 為唯一真相：授權變更與其操作稽核 MUST 同一交易落地；判定面 MUST 由真相同步導出，MUST NOT 存在繞過真相的第二寫入面。
- **FR-021**: 寫入成功（含空差異）後 MUST 同步判定面；被拒、無作用、標的不存在 MUST NOT 觸發同步。生效語意 MUST 明文：API 判定即時（每請求讀取新鮮授權）、前端選單／按鈕顯隱於下次載入更新；本刀 MUST NOT 做即時推播刷新。★**判定面同步失敗契約**（對抗式審查 Blocker，2026-07-12）：授權真相已落地（交易已提交）而判定面同步（全量重載）失敗時，系統 MUST 保留上一份已知良好的判定面、MUST NOT 使其空窗或半載（否則全體角色——含超級管理員——同時失去授權而全域鎖死，且治理面自身的救援端點亦一併失效、唯重啟可恢復）、MUST 發出結構化告警、MUST 有界重試至成功。降級窗口為「判定面有界陳舊」——沿既有「保留上一份已知良好」降級範式（008 FR-018）與授權面既有 fail-closed 紀律（`auth/enforce.rs` denylist Err→PG fallback）。此契約 MUST 有負向測試守門與留痕約定；判定面同步機制在失敗時是否會清空既有面（此即全域鎖死的技術根據）MUST 於 plan 期對實作核實。
- **FR-022**: 三維授權寫入、**授權復原（回收桶）**、與角色刪除／停用 MUST 互斥序列化——凡向現役授權寫入、或改動角色活性的寫端，MUST 於同一交易先鎖住標的角色列（`FOR UPDATE`）、鎖後重驗其判定前提（lock-then-redecide，憲法 §B2「永不信 pre-read」L-075），再落寫。★**授權復原的「可復原」判定（角色活性＋同實例）MUST 在鎖內重驗**，MUST NOT 以無鎖的預讀結果放行寫入（對抗式審查 Blocker，2026-07-12：restore-during-delete 競態下，無鎖預讀判 restorable 後才 INSERT，會讓一列現役授權逃過刪除的連動歸檔而殘留、被同代碼重建角色靜默繼承）。此不變式使「刪除／停用後殘留授權」與「同代碼重建繼承」在併發下均結構性不可達（守 FR-011／FR-012／FR-029）。
- **FR-023**: 選單維 MUST 以介面的選單識別收單、以穩定的路由名落授權，映射經活性選單資料轉換；已失效項 MUST 跳過（不產生孤兒授權）；讀端 MUST 反向轉換回介面識別。
- **FR-024**: 端點維授權粒度 MUST 為「路徑×方法」雙鍵；現況辨識 MUST 以方法白名單判別端點維（不得以「排除其他維度」反向推導）；MUST NOT 引入平行的維度標記編碼。
- **FR-025**: 三面板候選 MUST 與判定面同源：選單面板＝活性選單全集（樹狀）；按鈕面板＝活性選單登記的按鈕代碼聯集（去重）；端點面板＝系統路由登記表中受政策管制端點的全集。候選 MUST NOT 多列（不受管制者不出現）、MUST NOT 漏列。
- **FR-026**: 端點授權面板 MUST 以與另兩維一致的面板形式交付，候選依路徑群組呈現、支援群組級勾選。

#### 授權回收桶（US4）

- **FR-027**: 回收桶 MUST 以獨立管理頁交付（沿既有管理頁範式：查詢列＋表格＋分頁），列表以歸檔時間新到舊排列，MUST 支援來源角色與維度兩條件過濾；維度 MUST 由歸檔列內容推導（不新增維度欄）。
- **FR-028**: 每一歸檔列 MUST 附後端判定的「可復原」旗標（單一真相下發）；前端 MUST NOT 自行以來源標記字面推斷可復原性；旗標為否的列 MUST 呈現停用態。
- **FR-029**: 可復原判定 MUST 為：來源標記非「角色刪除」，且現存同代碼活性角色與歸檔列記錄的來源角色識別為同一實例。歸檔列無來源角色識別者（本刀結構變更前的歷史列）MUST 判為不可復原。
- **FR-030**: 復原 MUST 呈三態：可復原列→授權回到現役＋歸檔列移除＋操作稽核（同交易）；標的已在現役→回報成功（無作用）且歸檔列仍消費移除；識別不存在或不可復原→業務錯誤與專屬訊息。後端 MUST 為最終防線（縱深防禦，不依賴前端隱藏）。可復原判定與現役寫入 MUST 於鎖內序列化（FR-022，防 restore-during-delete 競態）。
- **FR-031**: 選單維的復原 MUST 另行驗證標的選單活性；已失效 MUST 拒絕（不灌無效授權）。
- **FR-032**: 回收桶選單項的三語譯文 MUST 隨頁補齊（不出現原始鍵字面）。

#### 拒因結構化明細（US5）

- **FR-033**: 每一種拒因 MUST 使用專屬訊息鍵（種子角色保護、掛載中、自身角色刪除、自身角色停用、代碼不可變、代碼重複、受保護撤銷、不可復原……一因一鍵），MUST NOT 以單一泛化訊息覆蓋多因。
- **FR-034**: 需要參數的拒因 MUST 經業務錯誤回應的既有明細欄下發插值參數（如掛載人數、被擋目標清單）；回應信封的欄位結構 MUST 不增不減；既有無明細的業務錯誤路徑 MUST 零改動。
- **FR-035**: 明細內容 MUST 以「該受眾本可經既有查詢能力自查的資訊」為限（洩漏面評估記入決策紀錄）；日後寫端授權下放時 MUST 連動重評明細通道的受眾邊界。
- **FR-036**: 全部新訊息鍵的三語譯文（含插值位）MUST 齊備。

#### 角色預設首頁（US6）

- **FR-037**: 每一角色 MUST 有預設首頁屬性，MUST 提供讀取與變更能力；變更候選＝系統頁面全集查詢。寫端 MUST NOT 強制首頁與選單授權的一致性（一致性由讀端兜底承擔，FR-039）。
- **FR-038**: 預設首頁變更 MUST 與操作稽核同交易落地；變更 MUST 於該角色成員下次登入或載入時生效。
- **FR-039**: 系統下發使用者路由時 MUST 驗證預設首頁屬於該使用者的可見路由：不屬於時 MUST 以其可見路由中的第一個可導航頁為落點；可見路由全空時 MUST 維持預設值。此兜底 MUST 覆蓋不一致的一切成因（首頁變更、選單撤銷、角色刪除重建、歷史資料），使「登入落 404」結構性不可達。

#### 資料結構

- **FR-040**: 本刀唯一資料結構變更 MUST 為：授權歸檔資料新增「來源角色識別」欄（可空；不設參照約束——歸檔列壽命長於角色列）。本刀之後產生的歸檔列 MUST 一律填值。

#### 本刀邊界（MUST NOT）

- **FR-041**: 本刀 MUST NOT 新增任何錯誤碼；回應信封結構 MUST 維持凍結。
- **FR-042**: 本刀 MUST NOT 交付保護旗標的管理能力（設定／解除皆不做）。
- **FR-043**: 本刀 MUST NOT 交付已刪角色的復原能力。
- **FR-044**: 本刀 MUST NOT 交付授權變更的即時推播（前端生效延遲為明文語意）。
- **FR-045**: 本刀 MUST NOT 交付寫端授權上限檢查（非超管寫端的「不得授出超過自身所有」防護）——本刀寫端結構上僅超級管理員可達、該檢查不可達；MUST NOT 於本刀下放任何寫端授權。此檢查 MUST 以待辦條目錨定為日後下放的前置。
- **FR-046**: 本刀 MUST NOT 變更任何種子資料（含角色名稱示範值與授權政策矩陣）；MUST NOT 做示範選單清理；MUST NOT 掛載列表排序參數。

### Key Entities

- **角色**：名稱、代碼（活性唯一、不可變）、描述、狀態（啟用／停用）、預設首頁、審計資訊；軟刪除。**結構已在凍結基線、本刀零變更。**
- **使用者-角色指派**：使用者與角色的多對多關係；本刀唯讀消費（守門判定、掛載計數），不提供指派寫入。
- **授權（現役）**：一列＝「某角色對某目標的某維度授權」；三維＝選單可見性、頁內按鈕、API 端點（路徑×方法）；帶保護旗標與治理欄位。**結構已在凍結基線。**
- **授權歸檔列**：被撤銷授權的完整快照＋來源標記＋歸檔時間／操作者＋**來源角色識別（本刀新增欄）**；回收桶的資料源。
- **選單登記**：活性選單全集（樹狀）與其登記的按鈕代碼；選單維候選與映射的真源。
- **端點登記表**：系統路由的單一登記面；端點維候選（受管制端點全集）的真源，與判定面同源。

- **SC-012**: 授權復原、三維寫入、刪除／停用在同一角色上的任意併發交錯，最終態 100% 等價於某一先後序列——特別是「復原與刪除交錯」100% 不殘留現役授權、同代碼重建 100% 不繼承（對抗式審查 Blocker 1 守門）。
- **SC-013**: 判定面同步（重載）於降級注入下失敗時，系統 100% 不發生全域授權鎖死（含超級管理員與救援端點可用）、100% 保留上一份已知良好判定面並發出告警；此為負向測試守門（刻意讓同步失敗時對應測試須證明不鎖死，對抗式審查 Blocker 2 守門）。

### 設計取捨（有意識接受）

- **角色 CRUD 能力的政策列非受保護**：技術上超級管理員可將其下放給其他角色；配合寫端授權上限檢查未建（FR-045）＝複合風險。圍堵手段＝「超管角色恆禁停用」結構護欄（FR-015）＋待辦條目錨定；v1 介面無下放誘因。
- **前端生效延遲**：授權變更後選單／按鈕顯隱等下次載入——明文語意（FR-021）、不做推播。
- **種子角色名稱為簡中示範值**：種子資料凍結不改；管理者可經編輯改名（執行期資料、非種子變更）。
- **回收桶多列歷史**：同一授權反覆撤銷會累積多列，屬預期；「已在現役→無作用」語意天然容納。
- **不提供解除保護**：受保護授權經介面永不可撤——防「把自己鎖出治理面」的設計；保護集的變更屬種子基線層級的決策，不屬執行期操作。
- **停用斷權為授權判定口徑的行為變更**：既有測試對角色活性口徑的斷言連動改寫；「全量角色」查詢的語意（本就註明僅啟用）與新口徑一致、無矛盾。

### 環境與驗收

- **實機瀏覽器驗收不可省**：面板的勾選樹、群組勾選、回讀一致性等互動語意無法以 API 呼叫等價驗證；驗收含以不同角色實際登入驗證選單／按鈕收縮（示範選單充當下放測試素材）。
- **停用斷權即時性須實測**：以受影響帳號的下一請求驗證（API 面），前端收縮於重新載入後驗證。
- **驗收具自傷面**：刪除／停用類驗收不得以操作者自身所屬角色為標的（會被自鎖防護正確攔下），須以測試角色與測試帳號進行。
