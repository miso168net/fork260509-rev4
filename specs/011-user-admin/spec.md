## Clarifications

### Session 2026-07-13（brainstorm 階段逐題親決，摘錄影響 scope 者）

- Q: 使用者寫端授權面（R_ADMIN 於 seed 有 manage_user 選單＋user:edit 按鈕，但寫端政策 super-only，構成「有鈕無權」不對稱）如何定？ → A: 寫端全維持 super-only、不對稱留置（B-083 不觸發）；R_ADMIN 見編輯鈕、點擊得誠實權限拒因；不對稱以 BACKLOG 條目錨定日後隨 demo 清理一併處理。
- Q: 改密相關兩路（管理員重設他人密碼 vs 使用者自助改密）哪些入刀？ → A: 管理員重設他人密碼入刀（B-029 主路、同交易撤該帳號全部 session）；使用者自助改密（user-center、需驗舊密）不入、留 BACKLOG 新條。
- Q: B-030（初始密碼隨機生成＋首登強制改密）做多深？ → A: 本刀僅做「admin 指定初始密碼＋密碼政策驗證」；隨機生成＋首登強制改密整包延後（首登強制改密需 sys_user 加欄＋login 插閘＋強制改密頁、且依賴自助改密能力）。
- Q: 刪除使用者時其角色指派列如何處置？ → A: 同交易硬刪指派列（零幽靈掛載使 009 刪角色守門與掛載計數誠實；復原後零角色＝復原不回灌，須管理者重新指派）。
- Q: 停用／刪除／改密的 session 撤銷即時性完備度？ → A: 以統一鎖序序列化並發登入（根治並發登入漏撤）；denylist 寫失敗時接受 ≤access token 壽命的殘留窗（由換發期活性守門兜底，沿既有降級範式）；不新增每請求的使用者活性判定。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理者能管理使用者的完整生命週期並指派角色 (Priority: P1)

超級管理員在使用者管理頁檢視分頁使用者列表（依帳號名／暱稱／電話／信箱模糊、性別／狀態等值過濾），新增使用者（設定帳號名、初始密碼、基本資料、狀態、角色指派），編輯使用者（基本資料／狀態／角色指派可改，帳號名恆不可變），以及刪除使用者（單筆與批次）。新增與重設密碼的密碼須通過系統密碼政策；刪除受 seed 帳號守門保護（三個 seed 帳號不可刪、操作者不可刪自己），過門的刪除為軟刪除且同一交易硬刪其角色指派列——同帳號名日後重建的新使用者不繼承任何舊角色。角色指派寫入與角色刪除／停用互斥序列化（跨刀併發守門）。

**Why this priority**: 這是頁面的基本價值，也是其餘故事的載體——沒有使用者生命週期，停用／改密／回收桶皆無標的。角色指派寫端是 sys_user_role 的第一個 production 寫入面，兌現 009 遞延的跨刀鎖序承諾。

**Independent Test**: 不需任何撤 session 或回收桶能力即可完整驗證——新增→查詢→編輯→刪除全鏈走通；seed 帳號守門與 self 守門逐案驗證；帳號名不可變驗證；角色指派提交後以受影響帳號實際登入驗證可達性；刪除後以同帳號名重建、驗證新使用者零角色。

**Acceptance Scenarios**:

1. **Given** 系統已有若干使用者，**When** 以帳號名模糊＋狀態條件查詢，**Then** 列表回符合條件的分頁結果，欄位含帳號名、暱稱、性別、電話、信箱、狀態、角色與建立／更新資訊，預設以穩定順序排列；回應 MUST NOT 含密碼或會話識別。
2. **Given** 搜尋欄留空（送空字串），**When** 查詢，**Then** 空字串等同未設該條件（不因空字串過濾導致整頁落空、不因數字欄空字串解析失敗導致請求錯誤）。
3. **Given** 新增表單，**When** 提交合法帳號名／初始密碼／基本資料／狀態／角色，**Then** 建立成功；帳號名與現存活性帳號名重複 MUST 回業務衝突與專屬訊息；初始密碼未過政策 MUST 回政策違規明細。
4. **Given** 已存在活性帳號名 X 的使用者，**When** 以帳號名 X 新增，**Then** 回業務衝突；**Given** 帳號名 X 的使用者已被刪除，**When** 以帳號名 X 新增，**Then** 成功（帳號名可重用）。
5. **Given** 編輯表單，**When** 嘗試變更帳號名，**Then** 被拒絕並回專屬訊息（帳號名不可變）；前端編輯模式帳號名欄亦鎖定（雙保險）。
6. **Given** 編輯請求未攜帶任何欄位變更，**When** 提交，**Then** 系統提前判定無作用：不更動時戳、不落操作稽核。
7. **Given** 新增或編輯的角色指派清單含未知或已刪的角色代碼，**When** 提交，**Then** 整批拒絕並回專屬訊息（不靜默丟棄）。
8. **Given** 三個 seed 帳號之一，**When** 刪除，**Then** 被拒絕（seed 帳號保護）。
9. **Given** 操作者自身帳號，**When** 刪除，**Then** 被拒絕（防自鎖）。
10. **Given** 通過守門的使用者，**When** 刪除成功，**Then** 該使用者為軟刪除，且其全部角色指派列於同一交易硬刪、其全部既有登入 session 於同一交易撤銷；操作稽核同交易落地且稽核內容不含密碼。
11. **Given** 批次刪除清單中任一項違反守門（含清單含已刪除的識別），**When** 提交批次，**Then** 整批拒絕、資料零變更（不可部分成功、fail-fast）。
12. **Given** 同一角色上「使用者指派提交」與「角色刪除／停用」併發，**When** 兩者交錯，**Then** 結果等價於某一先後序列——指派 × 刪角色守門不被繞過（跨刀鎖序）。

### User Story 2 - 停用、踢除或刪除使用者即時斷其存取 (Priority: P2)

超級管理員停用使用者（狀態改停用）、踢除使用者（撤其全部登入 session 但帳號仍活）、或刪除使用者後，該使用者的既有登入 session 即遭撤銷：踢除以阻斷式體驗（前端彈出「已被登出」提示），停用／刪除／改密以靜默登出。撤銷與業務寫入同一交易於權威儲存落定，失效廣播為 best-effort；並發登入不得造出撤銷漏網的 session。

**Why this priority**: 「停用／踢除」是斷權的正規手段，兌現 006 遞延的撤銷 primitive 消費端（B-064）。停用帳號的登入／換發斷權後端已預埋（005 forward-compat），本刀交付觸發端點使其生效。

**Independent Test**: 以測試帳號建立登入 session（雙瀏覽器），對其停用／踢除／刪除，驗證既有 session 於失效廣播後被拒、體驗碼（阻斷 vs 靜默）正確；並發登入序列化驗證不留漏網 session。

**Acceptance Scenarios**:

1. **Given** 某使用者持有效登入 session，**When** 管理者停用該使用者，**Then** 其 session 於撤銷廣播後被拒（靜默登出）；換發亦被既有活性守門擋下。
2. **Given** 某使用者持有效登入 session，**When** 管理者踢除該使用者，**Then** 其 session 被拒且前端呈現阻斷式「已被登出」提示；帳號仍為啟用，使用者可重新登入。
3. **Given** 停用帳號仍有殘餘 session，**When** 管理者踢除之，**Then** 殘餘 session 亦被撤（踢除不要求帳號為啟用）。
4. **Given** 操作者自身帳號，**When** 嘗試踢除，**Then** 被拒絕（防自斷；專屬訊息）。
5. **Given** Super（id=1）帳號，**When** 嘗試停用，**Then** 被拒絕（結構護欄）；**When** 踢除，**Then** 允許（無永久傷害、可重登）。
6. **Given** 某使用者即將被停用／刪除，**When** 其在撤銷交易提交前後並發登入，**Then** 不產生撤銷漏網的有效 session（統一鎖序序列化，並發登入於鎖內重驗帳號活性與密碼後才發 token）。
7. **Given** 停用後重新啟用，**Then** 既有 session 已撤，使用者須重新登入方能存取（語意自洽）。

### User Story 3 - 管理者能重設使用者密碼並即時斷其舊 session (Priority: P3)

超級管理員對任一使用者重設密碼（救援忘記密碼場景）。新密碼須通過系統密碼政策；重設成功後同一交易撤銷該使用者全部既有 session（舊密碼持有者立即失效），惟操作者對自己重設密碼時保留當前 session（不自斷）。密碼於全生命週期不外洩（不入日誌、不入稽核 payload、不入任何回應）。

**Why this priority**: 兌現 B-029 改密撤 session 主路，並使 004 已 seed 的密碼政策 7 鍵首度被真實執行。管理面重設覆蓋「忘記密碼」救援缺口（現制無任何改密路徑）。

**Independent Test**: 對測試帳號重設密碼，驗證舊 session 被撤、新密碼可登入、弱密碼被政策拒並回明細；操作者對自己重設驗證當前 session 保留；稽核與日誌不含密碼雜湊。

**Acceptance Scenarios**:

1. **Given** 某使用者持有效 session，**When** 管理者重設其密碼，**Then** 舊 session 於撤銷廣播後被拒、新密碼可登入。
2. **Given** 操作者對自己的帳號重設密碼，**When** 提交，**Then** 其他 session 被撤、當前操作 session 保留（不自斷）。
3. **Given** 重設的新密碼不符密碼政策，**When** 提交，**Then** 被拒並回政策違規明細（不落庫、不撤 session）。
4. **Given** 任一改密／建帳操作，**Then** 密碼明文與其雜湊 MUST NOT 出現於操作稽核、應用日誌、錯誤訊息或任何 API 回應。
5. **Given** 某帳號正處於登入節流鎖定中，**When** 管理者重設其密碼，**Then** 重設不解除節流鎖定；操作結果提示告知「若該帳號登入鎖定中需另行解鎖」。

### User Story 4 - 管理者能檢視回收桶並復原誤刪的使用者 (Priority: P4)

超級管理員在使用者管理頁切換「顯示已刪除」，檢視已軟刪的使用者（分頁、依刪除時間新到舊），對誤刪者一鍵復原。復原時系統於鎖內重驗同帳號名活性衝突（另有活性同名者→拒）；復原後使用者回到列表但零角色指派（復原不回灌，須管理者重新指派）、狀態保留刪除前原值。

**Why this priority**: 回收桶是「軟刪除」語意的救援閉環——與 009／010 回收桶對稱。沒有它，誤刪只能靠直接操作資料。依賴 US1 產生軟刪資料。

**Independent Test**: 軟刪測試帳號後於已刪除模式驗證列表、復原；復原後驗證零角色；另建活性同名帳號後嘗試復原被軟刪的同名帳號、驗證衝突被拒。

**Acceptance Scenarios**:

1. **Given** 使用者管理頁，**When** 切換「顯示已刪除」，**Then** 列表改呈已軟刪使用者（依刪除時間新到舊），操作欄改呈復原動作、隱藏新增／批次刪除。
2. **Given** 一個已軟刪使用者且無活性同名帳號，**When** 復原，**Then** 該使用者回到活性列表、零角色指派、狀態為刪除前原值、操作稽核落地。
3. **Given** 一個已軟刪使用者但已存在活性同名帳號，**When** 復原，**Then** 被拒並回專屬訊息（帳號名衝突；縱深防禦——鎖內重驗＋唯一約束兜底）。
4. **Given** 不存在的使用者識別，**When** 復原，**Then** 回業務錯誤（不靜默）。
5. **Given** 回收桶模式的頁面，**Then** 復原相關的三語譯文完整呈現（不出現原始鍵字面）。

### User Story 5 - 管理者能設定使用者的會話策略覆寫 (Priority: P5)

超級管理員可對任一使用者設定其會話策略覆寫（繼承全域／單一會話／多重會話）。設定即時落定，於該使用者下次登入時依既有解析階層（per-user 覆寫優先於全域）生效——改為單一會話不即時踢除既有多重會話（下次登入時收斂）。

**Why this priority**: 兌現 006 FR-004 遞延（per-user session_policy 設定 UI 留使用者管理刀）。欄位與後端解析階層、端點政策皆已預埋，本刀補交付端點與 UI。價值輕、風險低。

**Independent Test**: 對測試帳號設定會話策略、以該帳號登入驗證解析階層生效；編輯抽屜開啟時正確顯示該帳號現值。

**Acceptance Scenarios**:

1. **Given** 編輯抽屜，**When** 開啟，**Then** 會話策略選擇器正確顯示該使用者現值（讀取通道存在，不呈現預設值致誤判）。
2. **Given** 變更會話策略並提交，**When** 該使用者下次登入，**Then** 依 per-user 覆寫優先於全域的既有階層生效。
3. **Given** 會話策略無變更，**When** 提交編輯，**Then** 該欄不觸發寫入（no-op 判定）。
4. **Given** 會話策略改為單一會話，**When** 提交，**Then** 既有多重會話不即時被踢（下次登入時收斂），此為明文語意。

### User Story 6 - 管理者能手動解除登入鎖定 (Priority: P6)

超級管理員在使用者管理頁以頁首「解鎖」入口，選擇維度（帳號維／來源 IP 維）並輸入目標，手動解除登入節流鎖定。此為 007 遞延的解鎖 UI（API 與 super-only 政策已就位、純前端接線）。

**Why this priority**: 兌現 007 FR-021／B-061 note（解鎖 UI 隨使用者管理刀建頁補）。後端端點已活，本刀補前端入口與缺失的三語訊息鍵。列表不顯示鎖定態（權威態在快取、非資料欄）。

**Independent Test**: 對鎖定中的帳號經解鎖入口解鎖、驗證可再登入；非 super 呼叫驗證權限拒因；帳號維與 IP 維各驗一次。

**Acceptance Scenarios**:

1. **Given** 頁首解鎖入口（具對應按鈕權限），**When** 開啟，**Then** 呈現維度選擇（帳號／IP）與目標輸入。
2. **Given** 某帳號登入鎖定中，**When** 以帳號維解鎖，**Then** 該帳號可再登入（解鎖冪等）。
3. **Given** 來源 IP 鎖定中，**When** 以 IP 維解鎖並輸入合法位址，**Then** 該 IP 段解除；非法目標／缺目標 MUST 回專屬訊息。
4. **Given** 任一解鎖相關業務訊息，**Then** 三語譯文齊備、無原始鍵字面。

### User Story 7 - 拒絕原因帶具體明細 (Priority: P7)

管理操作被系統拒絕時（seed 帳號守門、self 守門、帳號名衝突／不可變、密碼政策違規、角色代碼無效、會話策略值域……），操作者看到專屬原因＋具體明細，而非泛化「操作失敗」。

**Why this priority**: 守門愈多，泛化訊息的挫折感愈重；具體明細讓操作者自助排除。依賴前六個故事產生的拒絕場景。

**Independent Test**: 逐一觸發各拒絕場景，驗證訊息含正確插值且三語齊備。

**Acceptance Scenarios**:

1. **Given** 密碼未過政策，**When** 建帳／重設密碼被拒，**Then** 訊息呈現具體違規項（如「至少 8 字」「須含數字」），非泛化訊息。
2. **Given** seed 帳號刪除、self 守門、帳號名不可變、帳號名衝突等拒因，**When** 觸發，**Then** 各以專屬訊息鍵呈現（一因一鍵）。
3. **Given** 既有無明細的業務錯誤路徑，**Then** 其行為與訊息完全不受本刀影響（零改動）。
4. **Given** 任一新拒因訊息，**Then** 三種語言的譯文（含插值位）齊備。

### Edge Cases

- **帳號名重用**：活性帳號名重複→衝突；已軟刪帳號名重用→允許，且新使用者不繼承任何舊角色（硬刪指派＋復原不回灌雙重封死；新使用者識別不同、角色指派以識別為鍵→授權零繼承）。
- **軟刪 × 復原併發**：兩者濾條件互補（未刪 vs 已刪），標的列鎖內重驗＋帳號名唯一約束兜底——先提交者勝、另一方見不存在或衝突，無雙活性同名。
- **復原 × 新建同名併發**：正確性由帳號名活性唯一約束保證（二者最後提交者撞唯一衝突）——此約束為本刀復原守門的顯式前提。
- **批次刪除含一項違規／含已刪識別**：整批拒絕、零變更（fail-fast、已刪識別視為違規非冪等）。
- **並發登入 × 撤銷**：統一鎖序序列化——停用／刪除／改密撤銷與登入互斥；登入於鎖內重讀帳號活性與密碼雜湊，序列化在撤銷後的登入見帳號已停用／已刪／密碼已變即中止、不發 token（堵住撤銷漏網 session；改密場景不留以舊密碼登入的漏網 session）。
- **失效廣播寫失敗**：撤銷於權威儲存已落定（session 已作廢），失效廣播 best-effort 失敗時，殘留窗上界＝access token 壽命（換發期活性守門為權威兜底、沿既有降級範式）——停用／刪除非 100% 即時、上界有界，明文接受。
- **合法撤銷後的換發**：被合法撤銷（停用／刪除／改密）者持既有換發憑證嘗試換發時，MUST 被靜默拒絕（不誤判為憑證盜用、不污染稽核）。
- **操作者停用／刪除自己**：self 守門拒（防自鎖）。
- **Super 帳號的各寫端**：不可刪、不可停用、不可解除其超管角色指派；可被踢除（可重登）、可重設密碼——「最後超管保護」不需動態計數即結構成立。
- **密碼多位元組**：密碼長度以字元計政策，另設位元組上界對齊登入端形制上限——不產生「設得進、登不進」的帳號。
- **密碼含帳號名**：政策開啟「禁止密碼與帳號名相同」時以大小寫不敏感相等比對（不因大小寫繞過）。
- **op-log 密碼遮蔽**：任何使用者寫端的操作稽核 payload MUST NOT 含密碼明文或雜湊、MUST NOT 含會話識別。
- **會話策略讀寫**：編輯抽屜以真實現值渲染會話策略選擇器——避免以預設值渲染致 diff 誤判而靜默弱化他人會話策略。

## Requirements *(mandatory)*

### Functional Requirements

#### 使用者查詢（US1）

- **FR-001**: 使用者列表 MUST 分頁，MUST 支援帳號名模糊、暱稱模糊、電話模糊、信箱模糊、性別等值、狀態等值過濾；預設以穩定順序排列（列表排序參數掛載不屬本刀）。搜尋參數 MUST 以「空字串等同未設」處理（空字串不作為過濾條件、數字類條件空字串 MUST NOT 導致請求解析失敗）。
- **FR-002**: 使用者列表與回收桶列表的回應 MUST 逐欄構造，MUST NOT 序列化原始使用者資料列——MUST NOT 含密碼（雜湊）與會話識別。列表 MUST 含該使用者現有角色（代碼）以供顯示與編輯回填。
- **FR-003**: 本刀全部能力的存取授權 MUST 沿用既有政策基線；已預埋於基線者不變更，四項新端點（重設密碼、踢除、回收桶查詢、復原）與四個按鈕代碼（reset-pwd／kick／restore／unlock——其中 unlock 為既有解鎖端點〔已預埋端點政策〕補欠缺之按鈕代碼、getDeletedUsers 端點無對應按鈕代碼）MUST 由顯式增量遷移新增授權政策（全授超級管理員、共 8 列）、MUST NOT 改寫凍結種子。各能力對外註冊的方法動詞 MUST 與政策逐條一致。
- **FR-004**: 使用者寫端授權 MUST 維持超級管理員專屬——本刀 MUST NOT 下放任何寫端授權至非超管角色；讀取列表既有政策授予超管與管理員兩角色（沿基線、不變更）。管理員角色於使用者頁的按鈕不對稱（見既有種子）MUST 以誠實權限拒因呈現，MUST NOT 為消除不對稱而改動種子（以待辦條目錨定日後隨示範資料清理處理）。

#### 使用者建立與編輯（US1）

- **FR-005**: 新增 MUST 接受帳號名、初始密碼、狀態，及選填的暱稱／性別／電話／信箱／角色指派；帳號名 MUST 通過形制守門——非空、僅限英文字母／數字／底線／連字號、長度上限 MUST NOT 超過登入端帳號名形制上限；帳號名形制與唯一性 MUST NOT 引入任何正規化（大小寫敏感、不 trim），與登入身分解析及節流判定鍵嚴格一致。與現存活性帳號名重複 MUST 回業務衝突與專屬訊息。
- **FR-006**: 帳號名 MUST 不可變——編輯請求試圖變更帳號名 MUST 被拒（專屬訊息）；前端編輯模式 MUST 鎖定帳號名欄（雙保險，消滅靜默無作用縫隙）。（帳號名為登入身分與節流判定鍵，允許改名將撕裂身分解析。）
- **FR-007**: 編輯 MUST 可改暱稱／性別／電話／信箱／狀態／角色指派；提交內容與現值全等（無任一欄位實際變更）時 MUST 提前判定無作用（不更動時戳、不落操作稽核）——no-op 判定 MUST 以「值與現值之 diff」為基準，MUST NOT 僅以「欄位是否缺席」為基準（前端全量提交下欄位恆帶值，「缺席即 no-op」不成立）。可空字串欄（暱稱／電話／信箱）送空字串＝清空；性別欄 MUST NOT 提供清空語意（本刀不引入非字串欄清空機制，B-026 部分兌現）。
- **FR-008**: 角色指派寫入（新增帶角色、編輯改角色）MUST 收角色代碼集合，於交易內映射為角色識別並鎖內重驗角色活性；未知或已刪的角色代碼 MUST 整批拒絕（專屬訊息、不靜默丟棄）。指派 R_SUPER 予任意使用者為合法操作（超管授權他人為超管）。★操作者 MUST NOT 變更自己帳號的角色指派（防自廢——尤其自解 R_SUPER；專屬訊息）；此為 FR-016 self 守門於「角色指派」維的延伸，與 FR-017（Super 帳號結構護欄）互補涵蓋「經自身帳號清空超管」的兩條路徑。
- **FR-009**: 編輯將狀態改為停用時 MUST 通過停用守門（FR-016、FR-017）；狀態改為停用 MUST 連動撤 session（FR-018/FR-021）。

#### 使用者刪除（US1／US2）

- **FR-010**: 刪除 MUST 依固定順序通過守門：①seed 帳號（識別為前三個種子帳號）不可刪 → ②操作者自身帳號不可刪。任一層擋下 MUST 回業務錯誤、零變更。
- **FR-011**: 批次刪除 MUST 逐項驗證、任一項違規則整批拒絕零變更（不可部分成功、fail-fast——首個違規即整批回滾並回該違規結構化拒因）；清單含已軟刪的識別 MUST 視為違規（非冪等跳過）；整個批次 MUST 於單一交易內完成、識別去重後以識別升序取鎖。
- **FR-012**: 通過守門的刪除 MUST 為軟刪除（成對寫入刪除時戳與刪除者），且 MUST 於同一交易：硬刪該使用者全部角色指派列、撤銷該使用者全部既有 session；操作稽核同交易落地。硬刪指派使「幽靈掛載」結構不可達（角色刪除的掛載計數守門保持誠實）。
- **FR-013**: 使用者刪除後其角色指派 MUST NOT 於復原時回灌（復原不回灌，見 FR-032）；刪除前的角色指派 MAY 以稽核 payload 快照留痕（但 payload MUST NOT 含密碼）。

#### 停用、踢除即時斷權（US2）

- **FR-014**: 停用中或已軟刪的使用者，其登入 MUST 被拒、其換發 MUST 被拒（此為既有預埋行為，本刀交付觸發使其在管理面可達；本刀 MUST NOT 破壞既有登入防枚舉三態不可區分語意）。
- **FR-015**: 系統 MUST 提供「踢除使用者」能力——撤銷某使用者全部既有 session（帳號仍活）；踢除 MUST 以阻斷式失效體驗（前端明示「已被登出」），MUST 允許帳號為停用態（可踢殘餘 session）。
- **FR-016**: 操作者 MUST NOT 能踢除／刪除／停用自己，亦 MUST NOT 變更自己的角色指派（防自斷／自鎖／自廢 R_SUPER；各以專屬訊息；角色指派維見 FR-008）。
- **FR-017**: Super（前述第一個種子帳號）MUST 恆禁停用、恆禁刪除、恆禁解除其超級管理員角色指派——不因操作者身分而異（結構護欄，保證系統恆有至少一個活躍且啟用的超級管理員）。Super MAY 被踢除（無永久傷害、可重登）。

#### 撤 session 連動（US2／US3、島 I2）

- **FR-018**: 系統 MUST 提供「撤銷某使用者全部既有 session」原語（既有撤銷 primitive 的變體，覆蓋並發換發後繼會話）。停用／刪除／改密 MUST 消費之並以「撤銷類」語意標記（靜默登出）；踢除 MUST 以「踢除類」語意標記（阻斷式登出）；兩類體驗碼 MUST NOT 互換（既有凍結語意）。
- **FR-019**: 撤銷動作序 MUST 為權威優先：業務寫入、session 作廢、稽核於同一交易於權威儲存落定 → 交易提交後失效廣播為 best-effort；失效廣播的存活時間 MUST 覆蓋換發憑證壽命（避免被撤者於換發窗換發後失效條目已過期而誤判為憑證盜用、污染稽核）。
- **FR-020**: 被合法撤銷（停用／刪除／改密）的使用者持既有換發憑證嘗試換發時 MUST 被靜默拒絕，MUST NOT 誤判為憑證盜用、MUST NOT 產生盜用稽核事件。
- **FR-021**: 停用／刪除／改密的即時性 MUST 有明文契約：失效廣播成功＝即時失效；失效廣播失敗＝殘留窗上界為 access token 壽命（換發期活性守門為權威兜底、沿既有「保留上一份已知良好／有界 fail-open」降級範式）。本刀 MUST NOT 為此新增每請求的使用者活性判定（不推翻既有分層），此殘留窗明文接受。

#### 並發序列化與鎖序（橫切、島 I1）

- **FR-022**: 一切**以既有使用者為標的**的使用者域寫端（含撤 session 者：更新、刪除、批刪、重設密碼、踢除、復原、會話策略）MUST 於交易起手取得與登入／換發同源的每使用者序列化鎖，使其與登入／換發互斥序列化；域內固定鎖序 MUST 為：①標的使用者列（`FOR UPDATE`；復原用已刪列版）→ ②角色列（僅指派路、識別升序、複用既有角色鎖讀）→ ③指派列寫入，禁反向。此鎖序 MUST 與既有角色域寫端鎖序無死鎖環。★**新增使用者（addUser）豁免**每使用者序列化鎖——其建立的新識別於交易提交前對並發不可見、且不涉既有 session 撤銷；其並發保護（同帳號名競態）由帳號名活性唯一約束（23505）承擔，非序列化鎖。
- **FR-023**: 登入流程 MUST 於序列化鎖內、發放 token 前重讀標的使用者列並重驗活性（狀態啟用且未軟刪）**與密碼雜湊**（與驗證階段所讀一致）；任一不符 MUST 中止登入、MUST NOT 發放 token。此 login 側重驗堵住「舊密碼 session 的產生入口」，使「並發登入造出撤銷漏網 session」與「改密後以舊密碼登入殘留 session」在併發下結構性不可達。換發流程 MUST 於既有換發憑證列鎖內重驗使用者活性（狀態／軟刪）——換發側**不另重驗密碼雜湊**（login 側已堵入口，換發只能延續已合法簽發的 session 鏈；漏撤保障由換發憑證列鎖鏈序列化＋活性 gate 承載，等價論證見設計研究）。
- **FR-024**: 所有守門判定 MUST 於鎖內重驗（lock-then-redecide），MUST NOT 以無鎖預讀結果放行寫入；使用者刪除／復原併發、指派 × 角色刪除併發、撤銷 × 登入併發的最終態 MUST 等價於某一先後序列。

#### 管理員重設密碼＋密碼政策（US3、島 I5）

- **FR-025**: 系統 MUST 提供「管理員重設使用者密碼」能力——新密碼 MUST 通過密碼政策；成功 MUST 於同一交易撤銷該使用者全部既有 session（改密撤 session），惟操作者對自己重設時 MUST 保留其當前 session（不自斷）。重設 MUST NOT 解除該帳號的登入節流鎖定（節流為獨立狀態）；操作結果 MUST 提示「若該帳號登入鎖定中需另行解鎖」。
- **FR-026**: 密碼政策驗證 MUST 為單一驗證點，建帳與重設密碼共用、零分叉；MUST 消費既有密碼政策設定鍵（最小長度、最大長度、需數字／小寫／大寫／特殊字元、禁止密碼與帳號名相同）。政策鍵 MUST 以單一快照讀取（避免逐鍵讀出跨快照的瞬時弱化政策）。
- **FR-027**: 密碼長度政策 MUST 明訂以字元計；驗證 MUST 另加固定位元組上界，該上界 MUST NOT 超過登入端密碼形制上限（避免多位元組密碼「設得進、登不進」）。「禁止密碼與帳號名相同」MUST 以大小寫不敏感相等比對（不因大小寫繞過）。
- **FR-028**: 密碼明文與其雜湊 MUST NOT 洩漏於任何面：承載密碼的請求資料 MUST NOT 以預設方式印出明文（除錯輸出遮蔽）；操作稽核 payload MUST NOT 含密碼明文／雜湊；API 回應 MUST NOT 含密碼；錯誤訊息 MUST NOT 回顯候選密碼。密碼雜湊計算 MUST NOT 於持有列鎖期間進行（避免拉長鎖持有期）。
- **FR-029**: 本刀 MUST NOT 交付使用者自助改密（user-center 驗舊密改密）；MUST NOT 交付初始密碼隨機生成與首登強制改密——初始密碼由管理員指定並經政策驗證。自助改密與首登強制改密 MUST 以待辦條目錨定為後續刀。

#### 使用者回收桶（US4、島 I4）

- **FR-030**: 系統 MUST 提供已刪除使用者查詢與使用者復原兩能力；回收桶 MUST 以同頁切換模式交付（顯示已刪除切換），已刪除列表以刪除時間新到舊排列。
- **FR-031**: 復原 MUST 於鎖內重驗同帳號名活性衝突（另存活性同名者→拒、專屬訊息；唯一約束為兜底），標的不存在→業務錯誤。復原成功 MUST 成對清除刪除時戳與刪除者、操作稽核同交易落地。
- **FR-032**: 復原 MUST 為零回灌——復原後使用者 MUST 零角色指派（須管理者重新指派方有授權）；狀態 MUST 保留刪除前原值（停用時被刪、復原後仍停用＝誠實）。
- **FR-033**: 回收桶相關的三語譯文 MUST 齊備（不出現原始鍵字面）。

#### per-user 會話策略（US5、島 A2）

- **FR-034**: 系統 MUST 提供 per-user 會話策略覆寫的讀取與變更能力（繼承全域／單一會話／多重會話）；讀取通道 MUST 存在（使用者列表回應含該欄），使編輯介面以真實現值渲染、MUST NOT 以預設值渲染致 diff 誤判而靜默弱化他人會話策略。
- **FR-035**: 會話策略變更 MUST 驗值域、MUST 於無變更時 no-op；生效語意 MUST 明文——依既有「per-user 覆寫優先於全域」解析階層於下次登入生效，改為單一會話 MUST NOT 即時踢除既有多重會話（下次登入收斂）。

#### 登入解鎖 UI（US6）

- **FR-036**: 系統 MUST 於使用者管理頁提供手動解鎖入口（消費既有解鎖端點、super-only 政策已備），支援帳號維與來源 IP 維；帳號維 MUST 要求帳號名、IP 維 MUST 要求可解析的位址目標，非法／缺目標 MUST 回專屬訊息。列表 MUST NOT 顯示鎖定態（權威態在快取、非資料欄；避免逐帳號查詢快取）。
- **FR-037**: 解鎖相關業務訊息鍵（含既有端點已使用但前端未建者）MUST 三語齊備、無原始鍵字面。

#### 拒因結構化明細（US7）

- **FR-038**: 每一種拒因 MUST 使用專屬訊息鍵（seed 帳號保護、self 守門〔刪除／停用／踢除／改自己角色指派〕、Super 結構護欄〔不可停用／不可解超管指派〕、帳號名不可變、帳號名衝突、密碼政策違規、角色代碼無效、會話策略值域……一因一鍵），MUST NOT 以單一泛化訊息覆蓋多因。（勘誤 2026-07-15 B-088：原列「不可復原」於實作拍板〔011 U10〕併歸「標的不存在」userNotFound、非獨立鍵。）

### Key Entities

- **使用者**：帳號名（活性唯一、不可變）、密碼（雜湊、不外洩）、暱稱、性別、電話、信箱、狀態（啟用／停用）、會話策略覆寫、審計資訊；軟刪除。**結構已在凍結基線、本刀零變更。** 前三個種子帳號受守門保護（皆不可刪；第一個〔Super〕額外不可停用、不可解超管指派）。
- **使用者-角色指派**：使用者與角色的多對多關係（複合鍵、硬刪、無審計）；本刀為其第一個 production 寫入面（指派／解除）；刪除使用者時同交易硬刪其指派列。
- **角色**：本刀唯讀消費（指派候選＝活性且啟用中的角色查詢；指派寫入時鎖角色列重驗活性）。
- **登入 session／換發憑證**：本刀唯讀消費既有撤銷 primitive；停用／刪除／改密／踢除為其撤銷觸發端。
- **密碼政策設定**：既有設定鍵集合；本刀為其第一個真實執行消費者（建帳／重設密碼驗證）。
- **登入節流狀態**：既有快取／稽核導出態；本刀提供手動解鎖入口，不新增其資料欄。
- **操作稽核**：使用者寫端與變更同交易落地；payload MUST NOT 含密碼與會話識別。
