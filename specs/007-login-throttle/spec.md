## Clarifications

### Session 2026-07-10

- Q: 登入輸入（`user_name`／`password`）現無任何長度或形制上限（DB 層亦無）。節流判定鍵＝帳號名原文，故輪換超長帳號名的攻擊者永不觸鎖、每發仍燒一次 memory-hard 雜湊並寫一列無界稽核列——要不要在節流閘之前把關？ → A: **加上限、超限回 `1000`**（沿用既有 `auth.login.failed`）：零稽核列、零雜湊運算、不消耗節流桶、零新 i18n 鍵。與既有「三態 collapse 1000」哲學一致（僅多一態）、與 FR-010「只有被雜湊驗證過的終局才落列」完全一致；長度為 client 自知之事，零新信號洩漏。字元集限制刻意不做（無正確性影響、YAGNI）。
- Q: 網路層速率限制（FR-017）被觸發時，nginx 自己回應、不進 rust-api、不走信封；前端 `onError` 的 `$t` 分支僅在「後端回 HTTP 200＋非成功碼」時觸發，故會顯示 axios 原生英文訊息。要回什麼、前端要不要接？ → A: **回 HTTP `429`、body 不作信封**，明文記為**基建層拒絕**（與反向代理的 `502`／`504` 同類），不受憲法 §I.3「信封普遍性」約束——該條文治理的是 rust-api 的 API 面，非反向代理自身的錯誤回應。前端零改動、零新 i18n 鍵、零攔截器 inline 風險；burst 設足使正常使用者與 CDP 驗收永不觸發。★同時勘誤 FR-017 的事實錯誤：限流區**並未宣告**（見該 FR）。
- Q: 無狀態改寫後，驗證碼的單次使用標記寫在「答案比對**之後**（相符才寫）」，導致同一張 challenge 可在其有效期內被反覆提交不同答案猜解——原有狀態設計（取出即刪）的「答錯即失效」性質在改寫時靜默遺失，且該改寫發生於對抗式審查之後、未經審查。要如何界定猜解阻力？ → A: **提交即消耗 ＋ 答案空間 ≥ 10⁶**。單次標記的寫入移到**答案比對之前**（簽章／有效期／帳號綁定驗證通過後即寫）：一張題只能作答一次，答錯即失效、必須重取新題——這既是使用者對驗證碼的普遍預期，也是原設計的本意。答案空間下界 10⁶（4 字元、不分大小寫英數字集＝36⁴＝1,679,616≈1.68×10⁶ 即已滿足）。★不重開 B1 的無界灌入面：產題仍零快取寫入，驗題路徑的寫入受 FR-017 網路層速率限制有界（峰值存活標記 ≈ 速率×有效期）。
- Q: 圖形驗證碼對視障／螢幕閱讀器使用者不可解，spec 對無障礙零提及。要提供替代通道嗎？ → A: **明文接受，記錄救濟通道**。驗證碼僅於軟區觸發（預設連錯 2 次後），日常登入不受影響；被擋者的救濟＝①等一個滑動窗自癒 ②由另一位超級管理員手動解鎖（FR-009）。★配套部署紀律：**至少保留兩個超級管理員帳號**（後台運維常規）。否決音訊驗證碼——語音辨識已成熟，音訊通道的自動化破解難度遠低於圖形，一旦提供即成為 B-018 緩解的**普遍後門**（攻擊者一律走音訊）。否決帳號級豁免旗標——攻擊者可探測出哪些帳號豁免並對其免摩擦鎖人，且加欄破 FR-015「零結構變更」。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 帳號級失敗節流（線上暴力猜密碼被擋下） (Priority: P1)

對同一帳號名連續猜密碼，在滑動時窗內失敗數達門檻後，該帳號名的後續登入嘗試一律被擋——即使送出的是正確密碼。
被擋時只得到一句**靜態一般化訊息**（語意如「登入失敗次數過多，請稍後再試」），不透露觸發維度、剩餘鎖定時間、
或帳號是否存在。攻擊者停手後鎖定隨時窗自然滑出而解除。合法使用者若在達門檻前成功登入一次，其失敗計數即歸零
（reset-on-success）——先前的幾次手滑不會累積到下次。

**Why this priority**: 這是本刀存在的頭號動機——005 明示「無節流鎖定」（FR-016 邊界），登入端點對線上暴力猜密碼
完全不設防。沒有它，argon2 的離線抗性在**線上**通道毫無意義。

**Independent Test**: 後端實測——同帳號名窗內連續錯密達門檻→後續嘗試（含正確密碼）一律被擋、回一般化訊息；
停手待窗滑出→自動恢復可登入；錯 4 次→成功登入→再錯 4 次→**不鎖**（reset 生效）。不存在的帳號名與真實帳號名
在被擋時得到**完全相同**的回應碼與訊息。本故事在 CAPTCHA 停用配置（門檻參數退化）下即可獨立交付與驗收。

**Acceptance Scenarios**（★本節場景以「驗證碼停用配置」表述，聚焦節流本身；與驗證碼的交互見 US2）:

1. **Given** 某帳號名於滑動窗內已累積達「失敗次數門檻」的失敗嘗試，**When** 再次送出登入（無論密碼對錯），
   **Then** 系統於**驗證密碼之前**即擋下、回 `2222`＋`auth.login.locked`（靜態一般化訊息）；不透露觸發維度、
   剩餘時間、帳號存在性。
2. **Given** 帳號已被鎖定，**When** 攻擊者停止嘗試、時窗內的失敗紀錄逐一滑出窗外，**Then** 鎖定自動解除、
   該帳號名恢復可登入；**鎖定的最長存續＝一個時窗**（自最後一次真實失敗起算）。
3. **Given** 某帳號名於窗內失敗 4 次（門檻為 5）後成功登入一次，**When** 其後再失敗 4 次，**Then** **不觸發鎖定**
   ——計數只數「最近一次窗內成功之後」的失敗。
4. **Given** 一個**不存在**的帳號名，**When** 對其連續猜測達門檻，**Then** 同樣被鎖定、回**與真實帳號完全相同**
   的碼與訊息（防枚舉：判定鍵為所送出的帳號名原文，不區分帳號是否存在）。
5. **Given** 帳號已被鎖定且鎖定判定的快取層已過期，**When** 下一次嘗試到達，**Then** 系統重查權威資料源後
   **仍判鎖定**、重新武裝快取、**且不新增任何登入嘗試稽核列**（鎖中被擋的嘗試不寫列、不延長鎖定）。

### User Story 2 - CAPTCHA 軟區（惡意鎖人的成本從零變成人工解題） (Priority: P1)

自動化工具若能免費地對他人帳號連續錯密，即可把任何人鎖在系統外（惡意鎖人 DoS）。本故事在「失敗數達到
**較低的軟區門檻**」之後、「達到鎖定門檻」之前，插入一道人機驗證：使用者須取得一張圖形驗證碼並填入正確答案，
該次登入嘗試才會被真正驗證。**缺少或答錯驗證碼的嘗試完全不計入失敗數、也不留稽核列**——否則自動化工具只要
持續送出不帶驗證碼的請求，照樣能把計數推到門檻、鎖住受害者。日常登入（尚未進入軟區）零摩擦。

**Why this priority**: B-018 的核心緩解。若無此層，鎖住任一帳號的成本＝送出「門檻次數」個 HTTP 請求，趨近於零；
有此層後成本＝人工解出「鎖定門檻 − 軟區門檻」張驗證碼。★「不計數不落列」是本故事的**安全支點**，一旦計數，
整個緩解歸零。

**Independent Test**: 後端實測——軟區前登入無需驗證碼；達軟區後不帶驗證碼→被拒且**窗內失敗列數不變**（灌 N 次
仍不觸鎖）；帶正確驗證碼→照常驗密碼並計數；同一張驗證碼二次使用→拒（單次使用）；為 A 帳號簽發的驗證碼用於
B 帳號→拒（綁帳號）；僅憑驗證碼本身無法還原其答案。CDP 實機：達軟區後登入頁出現驗證碼圖與輸入欄、可點圖換題。

**Acceptance Scenarios**:

1. **Given** 某帳號名窗內失敗數 `< 軟區門檻`，**When** 送出登入，**Then** 無需驗證碼、體驗與現況完全相同；
   即使請求帶了驗證碼欄位，系統亦**完全忽略**（不驗證、不消耗），該張驗證碼稍後進入軟區時仍可使用。
2. **Given** 某帳號名窗內失敗數 `≥ 軟區門檻` 且 `< 鎖定門檻`，**When** 送出登入且**未帶**驗證碼，
   **Then** 回 `2222`＋`auth.login.captchaRequired`；★該次嘗試**不計入失敗數、不落稽核列**。
3. **Given** 同上軟區狀態，**When** 送出登入並帶**錯誤／已過期／已使用過**的驗證碼，**Then** 同樣回
   `2222`＋`auth.login.captchaRequired`、★**不計數不落列**。
4. **Given** 同上軟區狀態，**When** 送出登入並帶**正確且未使用過**的驗證碼，**Then** 該驗證碼即刻作廢（單次使用）、
   系統照常驗證密碼；密碼錯→計一次失敗並落稽核列；密碼對→登入成功、失敗計數歸零。
5. **Given** 一張為帳號 A 簽發的驗證碼，**When** 於帳號 B 的登入請求中呈遞，**Then** 拒絕（驗證碼綁定帳號名，
   封死「預先大量取題、離線解好、跨帳號批次鎖人」）。
6. **Given** 帳號已進入**鎖定**狀態，**When** 送出登入並附上一張**有效**驗證碼，**Then** 仍回
   `2222`＋`auth.login.locked`（**硬鎖優先於驗證碼**）、且該驗證碼**不被消耗**（仍可在解鎖後使用）。
7. **Given** 攻擊者持續送出不帶驗證碼的登入請求（軟區內），**When** 送出任意多次，**Then** 窗內失敗列數
   **恆不變**、鎖定**永不被觸發**（緩解不被繞過）。

### User Story 3 - 超級管理員手動解鎖（誤鎖與惡意鎖人的救濟通道） (Priority: P2)

當合法使用者被鎖（自己手滑、或遭第三方惡意鎖定）且不願等待時窗自然滑出，超級管理員可呼叫解鎖能力立即恢復
該帳號名的登入。解鎖後，**窗內既有的舊失敗紀錄不再計入**——否則下一次登入嘗試會立刻以舊紀錄重新鎖定，解鎖
形同無效。每一次解鎖都留下操作稽核痕跡（誰、對誰、何時）。

**Why this priority**: 沒有它，被惡意鎖人的受害者只能等待一整個時窗（門檻可調至 24 小時）；且唯一的超級管理員
若被鎖，整個後台將無人可救。casbin 授權於基線已預先 seed（`POST /systemManage/unlockLogin`、super-only），
本刀消費之。

**Independent Test**: 後端實測——鎖定某帳號名→以超級管理員身分呼叫解鎖→**下一次登入嘗試不被 re-lock**、可正常
驗密碼；非超級管理員呼叫→`5003`；解鎖動作落恰一列操作稽核。

**Acceptance Scenarios**:

1. **Given** 帳號名 X 處於鎖定狀態，**When** 超級管理員對 X 呼叫解鎖，**Then** 鎖定即刻解除；X 的**下一次**
   登入嘗試不被窗內舊失敗紀錄重新鎖定（解鎖標記成為失敗計數的新起算下界）。
2. **Given** 解鎖已完成，**When** X 於解鎖後再次累積失敗至門檻，**Then** 正常重新鎖定（解鎖不是永久豁免）。
3. **Given** 一名非超級管理員，**When** 呼叫解鎖能力，**Then** 回 `5003`（授權拒絕）、不產生任何解鎖效果。
4. **Given** 任一次成功解鎖，**When** 查詢操作稽核，**Then** 可見恰一列記錄操作者、目標帳號名、時間。
5. **Given** 系統中唯一的超級管理員本人被鎖且無他人可解，**When** 其等待，**Then** 最長於**一個時窗**後
   自動恢復（鎖定存續上界＝時窗，非快取層存活時間）。

### User Story 4 - 基建降級不擋登入，且每次降級都發出告警 (Priority: P2)

節流的判定依賴權威資料源（失敗紀錄）與熱快取（鎖定負快取、驗證碼單次標記）。當任一基建故障時，**登入入口
不得因此全斷**——節流是縱深防禦、非強一致的關卡，儲存層抖動不該把全體使用者關在門外。同時，每一次降級都必須
發出可被監控系統擷取的**結構化告警訊號**，否則系統會在無人知曉的情況下裸奔。

**Why this priority**: rev3 的節流全鏈 fail-OPEN 但**零告警**（K2-01 批評點）——儲存層異常期間暴力嘗試完全不受
節流，卻沒有任何人會知道。本故事清償該缺口。降級方向一旦入憲即凍結（反轉為 MAJOR Amendment），故須在本刀
一次拍死。

**Independent Test**: 後端實測——逐一注入七個降級源（熱快取讀故障／驗證碼標記寫故障／失敗計數查詢故障／稽核寫入
故障／解鎖標記讀故障／設定讀取故障／負快取寫故障），斷言：①登入端點**不因故障而拒絕本應放行的登入**（唯一例外
見場景 4）②每一源各自發出帶來源標識的結構化告警訊號。

**Acceptance Scenarios**:

1. **Given** 鎖定負快取讀取故障，**When** 使用者登入，**Then** 系統退回權威資料源判定（節流**仍生效**、只是較慢），
   ★同時**整體停用驗證碼要求**（快取不可用時無法發題／驗題，合法與對抗流量同向放行、退化為「無驗證碼的節流」），
   並發出降級告警。
2. **Given** 失敗計數查詢故障，**When** 使用者登入，**Then** 視同計數為零、放行進入密碼驗證（fail-OPEN）；
   ★若熱快取仍可用，則**無條件要求驗證碼**（登入仍放行＝fail-OPEN，機器人阻力仍在＝fail-safe），並發出降級告警。
3. **Given** 登入嘗試稽核寫入故障，**When** 使用者登入失敗，**Then** 登入回應不受影響（沿襲既有 best-effort 語意）；
   ★但失敗計數因此斷供（永不鎖、永不進軟區），必須發出降級告警使維運可見。
4. **Given** 解鎖標記讀取故障，**When** 一個「剛被管理員解鎖」的帳號名登入，**Then** 系統以窗內舊失敗紀錄判定、
   可能將其**重新鎖定**——★此為全鏈 fail-OPEN 的**唯一 fail-closed 例外**（受影響集合僅限「一個時窗內剛被解鎖」
   的帳號、管理員可重解）；必須發出降級告警。
5. **Given** 節流門檻設定讀取失敗或值不可解析，**When** 使用者登入，**Then** 退回預設常數繼續運作（不中斷登入
   入口）、發出降級告警。
6. **Given** 任一降級發生，**When** 檢視觀測輸出，**Then** 可見一筆帶「安全節流」主題與「降級來源」欄位的
   結構化訊號（可供監控規則消費；具體告警規則配置屬觀測層刀）。

### User Story 5 - 節流稽核邊界（鑑識鏈完整，且不被壓制流量灌爆） (Priority: P3)

登入嘗試稽核必須能回溯「這個帳號為何被鎖」，但**不得**在鎖定期間為每一次被擋下的請求各寫一列——分散式暴力
攻擊會把稽核表灌爆，更嚴重的是「鎖中寫進去的列會落在自己的時窗內」，使鎖定被無限延長成永久鎖。本故事把稽核
邊界收斂為一句可驗證的規則：**只有被密碼雜湊實際驗證過的登入終局才落恰一列**；其餘（鎖中短路、驗證碼未過關）
一律零列，其量級改以觀測層的壓制訊號承載。

**Why this priority**: B-022「恰寫一筆與快取短路的邊界」的第一性重想。rev3 為此打了兩層 as-built 勘誤註記續命
（007 FR-004 exactly-one 被 021 反轉、019 FR-008 sticky 被反轉）；本刀一次寫成正式規則，終結勘誤鏈。

**Independent Test**: 後端實測六情境的稽核列增量（delta 斷言、非絕對計數）——鎖前成功／鎖前失敗／觸發鎖那一發
各恰一列；鎖中被擋（快取命中）／鎖中被擋（權威源再判）／驗證碼未過關 各**零列**；內部錯誤路徑不落列。

**Acceptance Scenarios**:

1. **Given** 帳號未鎖、未進軟區（或已附有效驗證碼），**When** 登入成功或失敗，**Then** 稽核表新增**恰一列**
   （沿襲既有語意：含帳號名、成敗、操作者、IP 取證最小版）。
2. **Given** 一次失敗使窗內計數達到鎖定門檻，**When** 該次嘗試落地，**Then** 仍是**恰一列**（它就是鎖定前的
   最後一次真實失敗、回 `1000`）——鎖定的成因於稽核中完整可回溯。
3. **Given** 帳號已鎖定，**When** 任意多次嘗試被擋下（無論快取命中或權威源再判），**Then** 稽核表**零新增列**；
   被壓制的量級改由觀測層訊號承載（含壓制計數，節奏受限、best-effort）。
4. **Given** 軟區內驗證碼缺失／錯誤／過期／重放，**When** 嘗試被拒，**Then** 稽核表**零新增列**（憑證從未被驗證、
   不構成登入終局）。
5. **Given** 內部錯誤（資料庫或設定異常）路徑，**When** 回 `5000`，**Then** 不落稽核列（沿襲既有語意）。

### User Story 6 - 超級管理員調整節流門檻 (Priority: P3)

超級管理員可於系統設定頁調整三個節流參數：失敗次數門檻、滑動窗長度（分鐘）、驗證碼軟區門檻。改值即時生效
（下一次登入判定即採新值），無需重啟。

**Why this priority**: B-032「runtime 可調門檻」的兌現。rev3 將其列為 v1-defer；rev4 因 004 的設定機制已完備
（新增設定鍵僅需 seed＋範圍宣告，兩端點與設定頁自動涵蓋），故本刀順勢落地。優先級為 P3——節流以預設值即可
交付價值，可調性是強化。

**Independent Test**: 後端實測——三鍵出現在設定查詢結果；各鍵超出宣告範圍的更新請求被拒（`2222`）；改值後
下一次登入判定採新值。前端實測：三鍵出現在設定頁「工作階段設定」分組、以數字控件呈現、附 i18n 標籤。

**Acceptance Scenarios**:

1. **Given** 超級管理員登入系統設定頁，**When** 檢視設定清單，**Then** 可見三個節流設定鍵（含 i18n 標籤與
   說明 tooltip），以數字控件呈現。
2. **Given** 超級管理員把「失敗次數門檻」由 5 改為 3（其餘設定不變），**When** 儲存後某帳號名於窗內失敗數
   達 3，**Then** 其後續嘗試即被鎖定——新值於**下一次登入判定**即生效，無需重啟。
3. **Given** 超級管理員送出超出宣告範圍的值（如次數門檻 = 0 或 101），**When** 儲存，**Then** 被拒絕（`2222`）、
   設定值不變。
4. **Given** 「驗證碼軟區門檻」被設為 `≥` 「失敗次數門檻」，**When** 使用者登入，**Then** 驗證碼要求實質停用
   （合法的退化配置：鎖定門檻先於軟區門檻達成）；節流本身照常運作。

### Edge Cases

- **時窗長於快取層存活時間**（時窗可調至 1440 分、快取存活上界為活書常數）→ 快取過期後由權威源再判、重新武裝
  快取，**且不寫稽核列**。★若在此路徑寫列，被寫入的列會落在自己的時窗內，攻擊者每隔一個快取存活期探測一次
  即可無限延長鎖定（且該路徑排在驗證碼閘之前、全程免解題）——此為設計必須排除的永久鎖迴圈。
- **鎖定負快取的唯一寫入者**＝權威源再判路徑。★失敗路徑本身**絕不**直接武裝快取：否則「一個並發的成功登入
  推進了計數下界、而失敗請求仍持有其密碼驗證前讀到的舊計數」會造出一把與權威源矛盾的**假鎖**，且快取短路使其
  在存活期內無法自癒。快取恆衍生自一次新鮮的權威源讀取。
- **並發失敗的計數超越量**：N 個同時在途的失敗請求各自讀到相同計數，最壞多寫 N−1 列。此為 check-then-act 的
  已知有界超越、可接受（每一發都是真實驗證過的失敗；軟區下各需一張有效驗證碼，攻擊者成本隨 N 線性上升）；
  鎖定必於下一個快取未命中的請求上咬合、不會漏設。
- **解鎖的兩步順序**：必須先寫解鎖標記、再刪鎖定快取。★反序會留下 race 窗——兩步之間的一擊登入會由權威源再判
  路徑以舊紀錄重新武裝快取，其後才落下的標記救不回來，解鎖名義成功、實際失敗。
- **未達軟區卻附上驗證碼** → 完全忽略（不驗證、不消耗）。★若在此消耗，合法使用者手上那張題會被白白用掉、
  真正需要時得重解。
- **熱快取不可用時的驗證碼要求** → 整體停用。★若保留「缺驗證碼即拒」而驗證碼又發不出來，合法使用者被死鎖在
  登入頁（實為 fail-closed）；若同時把「驗證碼校驗故障」判為放行，則攻擊者只要附上任意偽造的驗證碼識別碼即可
  被放行且失敗照常計數——降級恰好只放行對抗性流量。兩分支必須同向。
- **不存在的帳號名** → 同計數、同鎖定、同要求驗證碼；訊息與碼與真實帳號完全一致（防枚舉不變式的延伸）。
- **鎖定/驗證碼要求的回應不執行密碼雜湊** → 回應時間快於正常失敗數十毫秒。該差異揭露「該帳號名近期失敗數」，
  **不揭露帳號存在性**（真假帳號同鍵同計、同時進軟區與鎖定）。此為已知並接受的側信道。
- **驗證碼答案不可從驗證碼識別碼還原**：答案的驗證資訊須以伺服器秘鑰參與計算，否則短答案空間可被離線暴力還原、
  人機驗證形同虛設。
- **稽核寫入失敗** → 失敗紀錄未落地 ⇒ 計數斷供 ⇒ 永不鎖、永不進軟區（沿襲既有 best-effort 語意）；必須發出
  降級告警使其可見。
- **驗證碼取題端點為未認證可達** → 產題不得對共用熱快取產生寫入（否則未認證者可撐爆之，連帶影響會話撤銷的
  熱快取而使已撤銷會話在其憑證時效內續活）；產題的運算成本由網路層速率限制承擔。
- **本刀不觸 base-web 攔截器控制流**：`2222` 不在登出／阻斷式 modal 碼分組內，走既有一般錯誤提示通道。
- **輪換帳號名的資源消耗型攻擊**（clarify 2026-07-10）→ 每一發使用不同帳號名者，各自落入全新計數桶、
  ★per-user 節流**結構性無法涵蓋**（這正是「保護單一帳號不被猜穿」的定義，而非缺陷）。其資源成本由 FR-022
  （輸入形制上限：擋下超長輸入、零雜湊零落列）＋FR-017（網路層速率限制）共同承擔；聚合維度的防護遞延 IP 閘刀。
  ★per-user 節流 MUST NOT 被誤解為「總體請求速率的界」。
- **節流判定鍵與身分解析的正規化不一致**（clarify 2026-07-10）→ 同一帳號的多種寫法（大小寫等）各得一個獨立
  計數桶，節流可被繞過。現況兩者皆為精確比對（大小寫敏感）、一致；此一致性為 FR-001 的不變式，日後改動
  帳號查詢的正規化時 MUST 同步。
- **網路層限流被觸發**（clarify 2026-07-10）→ 反向代理直接回 `429`、請求根本不進 rust-api、不走信封；前端的
  `$t` 翻譯分支僅在「後端回 HTTP 200＋非成功碼」時觸發，故顯示通用錯誤訊息而非在地化文案。★已知並接受：
  在合理 burst 下正常使用者與實機驗收不會觸發，唯一會看到它的是攻擊者與壓測流量。
- **驗證碼答錯**（clarify 2026-07-10）→ 該張 challenge **即刻失效**（單次標記寫於答案比對之前），使用者須重取
  新題；前端 MUST 於答錯時自動重取（FR-018）。★若改為「答對才消耗」，同一張題可在其有效期內被反覆猜（在合理
  限流下約上千次），阻力全壓在答案空間與網路層限流兩處；且「答錯不換題」不符使用者對驗證碼的普遍預期。
- **驗證碼簽章／有效期／帳號綁定驗證失敗** → 不消耗任何單次標記（那本就不是該帳號的一張有效題）；與「答錯」
  （消耗）語意不同。
- **視障／螢幕閱讀器使用者遇上圖形驗證碼**（clarify 2026-07-10）→ 不可解。★已知並明文接受：驗證碼僅於**軟區**
  觸發（預設連錯 2 次後），日常登入零影響；被擋者的救濟通道有二——①等一個滑動窗自癒 ②由**另一位**超級管理員
  呼叫手動解鎖（FR-009）。配套部署紀律：**至少保留兩個超級管理員帳號**。★否決音訊驗證碼（語音辨識成熟、
  自動化破解難度遠低於圖形，一旦提供即成為 B-018 緩解的普遍後門）與帳號級豁免旗標（可被探測、對最需保護的
  帳號開繞過口，且破 FR-015 零結構變更）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 於登入端點、**密碼雜湊驗證之前**實作**帳號級失敗節流判定**：以「送出的帳號名原文」為判定鍵
  （不區分帳號是否存在——防枚舉），統計滑動時窗內該鍵的失敗嘗試數；達「失敗次數門檻」即擋下後續嘗試。
  判定 MUST NOT 依賴請求來源 IP（見 FR-021 邊界）。判定於 FR-022 的輸入形制檢查**之後**執行。
  ★**判定鍵的正規化 MUST 與帳號身分解析的正規化嚴格一致**——否則同一帳號的多種寫法各得一個獨立計數桶、節流即可
  被繞過。現況兩者皆為所送出字串的精確比對（大小寫敏感、零正規化）；若日後令帳號查詢改為大小寫不敏感，
  節流鍵 MUST 同步正規化。
- **FR-002**: 失敗計數 MUST 實作 **reset-on-success**：只統計「最近一次落在時窗內的成功登入之後」的失敗嘗試。
  （成功登入即為天然重置點，不需額外寫入。）
- **FR-003**: 被節流擋下的嘗試 MUST 回 `2222` ＋ 穩定 i18n key `auth.login.locked`，且該訊息 MUST 為**靜態一般化
  文字**：MUST NOT 透露觸發維度、剩餘鎖定時間、或帳號存在與否。不存在帳號名與真實帳號名的回應 MUST 完全一致。
- **FR-004**: 系統 MUST 以**負快取層**短路已生效的鎖定（命中即擋、零權威源查詢、零密碼雜湊）。負快取
  MUST 僅由「權威源再判路徑」寫入——**失敗路徑本身 MUST NOT 直接武裝負快取**（保證負快取恆衍生自一次新鮮的
  權威源讀取，杜絕與權威源矛盾的假鎖）。負快取命中 MUST NOT 續期（防「每隔不到存活期戳一下即永久鎖死」）；
  其存活時間 MUST 不長於時窗（防「快取比權威源多鎖」）。
- **FR-005**: 鎖定期間被擋下的嘗試（無論負快取命中或權威源再判）MUST NOT 寫入登入嘗試稽核列；其量級 MUST 以
  觀測層壓制訊號承載（節奏受限、best-effort、非稽核表）。★權威源再判路徑 MUST NOT 寫列——否則該列落入自身
  時窗，使鎖定可被免驗證碼的週期性探測無限延長。**鎖定的最長存續＝一個時窗**（自最後一次真實失敗起算）。
- **FR-006**: 系統 MUST 於「窗內失敗數 ≥ 軟區門檻」時要求**人機驗證（圖形驗證碼）**。驗證碼 challenge MUST：
  ①**綁定所送出的帳號名**（跨帳號呈遞即拒）②帶有效期 ③其答案 MUST NOT 可自 challenge 本身還原（答案驗證資訊
  須以伺服器秘鑰參與計算）④**答案空間 ≥ 10⁶**（4 字元、不分大小寫英數字集＝36⁴＝1,679,616≈1.68×10⁶ 即已滿足；
  字元數與字元集入活書常數）。
  ★**提交即消耗**（clarify 2026-07-10）：單次使用標記的寫入 MUST 發生於「簽章／有效期／帳號綁定」驗證通過**之後**、
  「答案比對」**之前**——一張題只能作答一次，**答錯即失效、必須重取新題**；標記已存在＝重放 → 拒。
  取題 MUST 由獨立的未認證可達端點提供，且**產題 MUST NOT 對共用熱快取產生任何寫入**（寫入僅發生於驗題路徑、
  且受 FR-017 的網路層速率限制有界）。
- **FR-007**: 軟區內**缺少／錯誤／過期／重放**的驗證碼 MUST 回 `2222` ＋ `auth.login.captchaRequired`，且該次嘗試
  ★MUST NOT 計入失敗數、MUST NOT 落稽核列（憑證從未被驗證、不構成登入終局）。★此為 B-018 緩解的安全支點：
  一旦計數，自動化工具只需送出不帶驗證碼的請求即可推滿計數、鎖住任意帳號。
- **FR-008**: **硬鎖優先於驗證碼**：帳號已鎖定時，即使呈遞有效驗證碼亦 MUST NOT 受理，且該驗證碼 MUST NOT 被
  消耗。**未達軟區時 MUST 完全忽略請求所帶的驗證碼欄位**（不驗證、不消耗）。
- **FR-009**: 系統 MUST 新增超級管理員專屬的**手動解鎖能力**（消費基線已 seed 的 `POST /systemManage/unlockLogin`
  授權；非超級管理員 → `5003`）。解鎖 MUST：①寫入「解鎖標記」使其時刻成為失敗計數的新起算下界（登入嘗試稽核
  為 append-only、舊失敗列不可刪，若不設下界則下一擊立即以舊列重新鎖定）②清除鎖定負快取
  ③★**依此順序**（先標記、後清快取）——反序留下 race 窗，兩步之間的登入會以舊列重新武裝負快取而使解鎖失效
  ④落恰一列操作稽核（操作者、目標帳號名、時間）。
- **FR-010**: 登入嘗試稽核邊界 MUST 收斂為：**只有被密碼雜湊實際驗證過的登入終局才落恰一列**；鎖定短路、
  權威源再判、驗證碼未過關、**輸入形制超限**（FR-022）一律零列；內部錯誤（`5000`）路徑不落列（沿襲既有語意）。
  此規則 MUST 取代 005 FR-003／SC-002 的「每次登入終局恰一列」口徑，其守門測試 MUST 連動改寫。
- **FR-011**: 節流子系統 MUST 全鏈 **fail-OPEN**（定義＝不因基建故障而拒絕本應放行的登入），涵蓋下列降級源，
  各自方向如下：
  ①**負快取讀故障** → 退權威源判定（節流仍生效）＋★整體停用驗證碼要求；
  ②**驗證碼單次標記寫故障**（熱快取健康時的瞬斷）→ 拒絕該次嘗試但**零計數**（與缺／錯驗證碼同向、不懲罰）；
  ③**失敗計數查詢故障** → 視同計數為零、放行進密碼驗證；★若熱快取可用則**無條件要求驗證碼**（登入 fail-OPEN、
  機器人阻力 fail-safe）；

### Key Entities *(include if feature involves data)*

- **登入嘗試稽核（既有 append-only 表）**：本刀同時為其**寫者**（沿襲）與**讀者**（滑動窗計數源）。欄含帳號名、
  成敗、操作者、時間、IP 取證最小版；帳號名×時間與來源位址×時間兩複合索引於基線已備。本刀不改其結構。
- **失敗計數（衍生值，非持久實體）**：某帳號名在「時窗起點、最近窗內成功時刻、解鎖標記時刻」三者取最晚者之後的
  失敗嘗試數。權威來源＝登入嘗試稽核表。
- **鎖定負快取**：帳號名 → 鎖定生效時刻；為權威判定的快路徑，其存在**非**權威（絕不作為鎖定的真相來源）；
  唯一寫入者＝權威源再判路徑；命中不續期。
- **解鎖標記**：帳號名 → 解鎖時刻；作為失敗計數的起算下界之一。存於熱快取（揮發性為已知取捨、見 FR-011 ⑤）。
- **驗證碼 challenge（無狀態）**：伺服器簽名的識別碼，載有一次性隨機值、綁定的帳號名、有效期、與**不可逆的
  答案驗證資訊**。取題不落任何伺服器端狀態。
- **驗證碼單次使用標記**：一次性隨機值 → 已使用。於「簽章／有效期／帳號綁定」驗證通過**之後**、答案比對**之前**
  寫入（**提交即消耗**，clarify 2026-07-10）；存活期＝challenge 有效期。★寫入僅發生於**驗題**路徑（產題零寫入），
  且受 FR-017 網路層速率限制有界——峰值存活標記 ≈ 限流速率 × challenge 有效期。
- **節流門檻設定（三個 number 設定鍵）**：失敗次數門檻、滑動窗分鐘數、驗證碼軟區門檻；沿用既有設定機制
  （查詢端點自動涵蓋、更新端點依 per-key 範圍驗證）。
- **降級告警訊號（觀測層）**：帶固定主題與「降級來源」欄位的結構化訊號＋預埋計數器；非稽核表列。
- **壓制量麵包屑（觀測層）**：鎖定期間被擋下的嘗試量級；節奏受限、best-effort、非稽核表列。

## Assumptions

- **資料面沿用 baseline、零結構變更**：登入嘗試稽核表（append-only、11 欄）與其「帳號名×時間」「來源位址×時間」
  兩複合索引於基線已備；其 `region` 欄維持恆空。本刀唯一 migration＝三個設定鍵的增量 seed。
- **熱快取基建沿用 006（ADR 0033）**：自動重連連線管理器已在 `AppState`；「缺席（`Ok(None)`）」與「連線故障
  （`Err`）」的嚴格分流語意（R7）為本刀降級矩陣的前提，本刀所有讀取沿用同一底座。★測試 stub 的「無熱快取」
  狀態視同「熱快取讀故障」（節流走純權威源、驗證碼要求停用）。
- **設定機制沿用 004（ADR 0026）**：新增設定鍵僅需 seed＋per-key 範圍宣告；查詢端點（回全列）與更新端點
  （依範圍驗證）自動涵蓋，handler／router／casbin 零改動。門檻讀取**不加快取**（鎖定熱路徑已由負快取短路），
  故本刀**不是**「首個快取消費者刀」、不兌現設定失效通知的 documented-stub。★軟區的「缺驗證碼」請求為未被負快取
  隔離的熱路徑（每發一次設定讀＋一次計數查詢），其成本記入 ADR 0038、真實量級閘為 FR-017 的網路層限流。
- **授權沿用**：`POST /systemManage/unlockLogin` 的 super-only casbin 政策於基線已 seed，本刀消費、零新 seed。
  操作稽核詞彙需新增一個變體（既有註解本就預告「隨消費刀進場再加」）；解鎖的業務寫入落於熱快取、無法與操作
  稽核共交易，故操作稽核採**單寫 best-effort**（失敗告警、不回滾已生效的解鎖；解鎖冪等可重試）。
- **加密與依賴**：驗證碼 challenge 的簽章與答案驗證資訊複用既有已釘版的 JWT（HS256＝HMAC-SHA256）與 SHA-256
  能力，**零新增 crypto 依賴**；答案比對採常數時間。**唯一新 crate ＝圖形驗證碼產圖**，其版本於 plan/implement 期
  雙源查核（crates.io 最新 stable × rev3 有無先例）後**攤兩案給 user 選**（全域 §6 版本紀律）；不用 `git+`/HEAD 源、
  不收 pre-release。新增一組 secret（沿 `_FILE` 優先＋boot fail-loud 慣例）供 challenge 簽章，與 JWT 雙秘鑰隔離。
- **測試機制先決（★實作期必須先建，否則對應守門寫不出來、會退化成恆綠）**：①失敗計數查詢的**故障注入接點**
  （測試組建限定）②結構化告警的**捕捉層**（測試組建限定、收集主題與來源欄位；零新依賴）③**指定稽核列時間戳**
  的能力以構造窗過期情境（既有測試清理函式對同表已有直接 SQL 先例）④測試端以同一簽章秘鑰**自簽 challenge**、
  答案自持（免解圖）。★守門測試 MUST NOT 以「改設定全域值」繞開軟區（共享狀態污染）。
- **並發語意**：失敗路徑沿襲既有「全程無交易、無序列化」的形狀（不對其加鎖，避免連線耗竭面）；check-then-act 的
  計數超越量上界＝同時在途的失敗請求數 −1（有界、可接受），鎖定於下一個負快取未命中的請求上咬合。
- **per-user 節流的射程（clarify 2026-07-10）**：判定鍵是攻擊者可控的帳號名，故本刀保護的是「**單一帳號不被
  暴力猜穿**」，**不是**「總體請求速率的界」。輪換帳號名的資源消耗型攻擊由 FR-022（輸入形制上限）與 FR-017
  （網路層速率限制）承擔，聚合維度的防護遞延 IP 閘刀。既有 `dummy_verify`（防枚舉時序拉平）意味著每一個
  通過形制檢查的未知帳號名仍會消耗一次 memory-hard 雜湊——此為防枚舉的**既定代價**，非本刀引入。
- **rev3 為唯讀受控參照（§I.5、防回歸條款）**：019 登入節流（滑動窗、一般化訊息、fail-OPEN、per-user 門檻起始值
  ——承襲；per-ip 維度與 sticky 逐筆審計——**翻案**）、021 負快取（承襲設計、調整存活時間）、022 解鎖標記形
  （承襲）、013 XFF 取證（**不承襲、不重建**）。code 不拷貝。
- **驗收面**：rust build/test 一律容器內、全程 serial（host 無 toolchain）；base-web 無測試框架 → 靜態閘
  （build／typecheck／lint／locale 對等／契約對齊）＋CDP 實機走查。★review 輪受非破壞紀律約束——**禁觸發鎖定**
  （L-055）；多 reviewer 各自登入會污染登入嘗試甚至觸鎖、把稽核斷言弄成偽紅（L-057），須共用 token。
- **本刀邊界（能力已備、觸發遞延）**：per-IP 維度／XFF 防偽解析／IP 白名單跳節流 → IP 閘刀（B-019/B-024、
  ADR 0017）；地理解析 → 新條目；手動解鎖 UI → manage 頁刀（route locale key 須隨建頁走）；grafana 告警規則實配／
  來源廣度估計／IP 維 TTL 拆分 → 觀測層刀（B-033 殘餘）；手機/信箱真驗證 → B-028（本刀的驗證碼底座可複用、
  命名空間已分隔——既有 `captcha` 一詞指簡訊驗證碼）。★節流判定點落於密碼登入的核心路徑，替代登入端點未來
  轉真時**不自動涵蓋**。
- **B-018 誠實定位**：本刀提供三層緩解（驗證碼軟區、手動解鎖、網路層限流），但**未徹底消滅**惡意鎖人——驗證碼
  可被人工／ML 農場破解，鎖死一個帳號的成本＝解出「鎖定門檻 − 軟區門檻」張題（預設 3 張）。徹底緩解需 IP 信任
  白名單（IP 閘刀）或信任裝置；殘餘另立條目。
- **無障礙定位（clarify 2026-07-10）**：本刀**不提供**圖形驗證碼的無障礙替代通道。理由＝觸發面極窄（僅軟區、
  日常登入零影響）＋救濟通道已存在（等窗自癒／他人解鎖）＋音訊替代會成為 B-018 緩解的普遍後門。★**配套部署
  紀律：至少保留兩個超級管理員帳號**——否則唯一的管理員一旦被鎖（無論成因），除等待滑動窗外無救濟手段。
  此紀律亦是既有「唯一 Super 被鎖」邊角（US3 場景 5）的通用解。
