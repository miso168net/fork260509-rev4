## 〔環境與工具鏈（WSL2／docker／cargo／vite）〕

- **L-179**｜**自動化「互動式解密」時，「等提示才餵」與「盲餵」各有一個坑，兩個都會咬人**——
  019 撤銷演練以 pty 驅動 `deploy/decrypt-secrets.sh`：①**等提示才餵＝必然 timeout**。腳本把
  sops 的 stdout（提示行與解密輸出**同一條容器 pty 流**）重導向進暫存檔，pty 流上因此**永遠
  不會出現** `Enter passphrase…`；以該字串當觸發錨的驅動器就一直等到自己的 deadline，看起來
  像「解密卡死」，實際是**觸發錨選在一條被重導向的流上**。②改盲餵（以腳本自己印的預告行為
  錨）解決 timeout，卻踩第二格：預告行是 **host shell** 印的、此時容器還沒接管 tty，寫進去的
  字元被 host 行編輯**回顯**——passphrase 於是以明文留在捕捉檔與畫面 scrollback（實測同一支
  驅動器的 `ECHO_LEAK` 欄位由 0 變 1；換成容器已接管後才餵的呼叫則恆 0）。
  ｜防法：①判斷「提示是否看得到」以**該流有沒有被重導向**為準，別用「互動程式總會印提示」
  推定；②盲餵的捕捉檔一律**視同機密**（700 目錄、驗畢即刪），且驅動器要有 `ECHO_LEAK`
  之類**機判欄位**（捕捉檔中 passphrase 出現次數）——只看畫面看不出回顯；③這條同時是**操作面
  結論**：真人操作也一樣，搶在容器起來前打字就會把 passphrase 打在畫面上——RUNBOOK §15 已
  收錄「等容器起來再輸入」的提醒。｜出處：2026-07-29 019 U5（T033 撤銷演練；首次呼叫
  timeout 120s 零寫入、改盲餵後 rc=0／8 支 WRITTEN／零 `.new`）

## 〔git／worktree／submodule〕

- **L-191**｜**值比對層「擋下 commit」不等於機密沒進物件庫；而 L-158 的稽核法對「文件內含機密」
  結構性失明、會回報假綠**——019 U6 改落點語彙時，pre-commit 值比對層擋住 commit（正確擋），
  但 `git add` 早已把兩支含 `alert_webhook_url` **完整字面**的檔（RUNBOOK 與 dev-webhook-sink.sh
  的修前版、54857 與 2228 bytes）寫成 unreachable loose blob——**擋的是 commit、不是 `git add`**。
  收刀終驗照 L-158 防法②跑「`git hash-object <機密檔>` × `git fsck --unreachable` 取交集」得
  **交集 0＝假綠**：那兩個 blob 不是「**等於**機密檔」而是「**含**機密值為子字串」，SHA 相等判準
  結構上碰不到它。同理 `git rev-list --all --objects` 的 SHA 交集也回 0。
  ｜防法：①稽核判準升級為**內容子字串比對**——`git fsck --unreachable` 逐筆 `git cat-file blob`
  讀出、判「是否含任一落點現值為子字串」（只印 SHA 前 8 碼與 size，**不印內容**）；②凡被事件型
  防線擋下過的 commit，收尾必跑 `git prune --expire=now`＋反證（兩 blob `cat-file -e` rc≠0、
  含機密之 unreachable blob 數歸零）；③**unreachable blob 數本身即指標**——非零就逐筆看，別只看
  交集；④同一輪順手核 HEAD tree（`git ls-files` × `git show HEAD:` 子字串掃）與 rev-list 可觸及面，
  區分「只需 prune」與「已進歷史＝要輪替＋改寫歷史」。
  ｜出處：2026-07-30 019 U6 T038 收刀終驗（本輪實測：unreachable blob 2 筆皆含現值 → prune →
  歸零；HEAD tree 子字串掃命中 0；兩 blob 皆不可由任一 ref 觸及＝未進歷史故無須改寫）。
  ★**出處末句之推論已由 L-196 更正**：「那兩個 blob 不可由 ref 觸及」為真、但「＝未進歷史」為假。

- **L-196**｜**判準只升級一個面＝假綠照樣成立：同一輪把 unreachable 面從 SHA 相等改成子字串掃、
  可觸及面卻用回 SHA 相等，就得到假的「未進歷史」**——L-191 剛親自點名「SHA 相等判準對『檔案
  **內含**機密』結構上碰不到」，其收尾卻以「那兩個 blob 的 SHA 不在 `rev-list --all --objects`」
  斷言機密未進歷史；改以同一子字串判準重掃可觸及面（1717 個 blob）即得 **20 個含 `alert_webhook_url`
  現值之可觸及 blob**（19 個 `docs/ops/RUNBOOK.md` 歷史版＋1 個 `deploy/dev-webhook-sink.sh` 舊版，
  其中 **12 個是本刀自己 commit 寫進去的**、只在 HEAD 版被改述掉）。危害不在該值本身（dev 收器
  容器內部位址、已誠實登記為 dev-only 已接受殘餘），而在這一步是「**只需 prune** vs **已進歷史
  ＝要輪替＋改寫歷史**」的唯一判準——照那份劇本處置真機密會直接跳過輪替與歷史改寫。加重因子：
  L-191 防法④ 與 quickstart 原文都只寫「併核 rev-list 可觸及面」而沒寫**用什麼判準**核，語意空缺
  就會被最順手的舊判準填滿。
  ｜防法：①**判準升級一律全面同步**——寫下「三面（unreachable／HEAD tree／rev-list 可觸及）
  一律子字串掃」並在劇本逐面寫出命令，禁止任何一面留「併核」這種未指定判準的字眼；②可觸及面
  掃法＝`git rev-list --all --objects` 取全物件 → `git cat-file --batch` 串流 → 命中者以
  `rev-list --objects` **反查路徑**（路徑才看得出是文件還是機密檔），另限縮 `<merge-base>..HEAD`
  算出「本刀新引入」子集；★**掃描母體不限物件型別、且 unreachable 面要加跑 `--no-reflogs`**
  （019 final review 兩項實證：機密值也可能寫在 **commit message**〔本 repo 有 1 筆 016 期 commit
  物件含該值〕，只掃 blob 對整個型別失明——改用 `git cat-file --batch-all-objects --batch` 掃全
  物件；而 `git fsck --unreachable` 預設把 reflog 當根，**僅 reflog 可觸及的舊 blob 看不到**、
  `prune --expire=now` 亦不清，需 `git reflog expire --expire-unreachable=now --all` 再 `gc`）；
  ③命中≠0 必走**分流表**：真機密→輪替＋改寫歷史（缺一即未結清）／
  dev 佔位無憑證材料→可判已接受殘餘但必須誠實登記，**不得寫成「未進歷史」或「暴露面已關閉」**；
  ④凡自己剛在同一段文字裡指出某判準失明，就把該段所有沿用舊判準之處一併枚舉改掉（同 CLAUDE.md
  勘誤紀律：禁止只修被點名那一處）。
  ｜出處：2026-07-30 019 U6 T038（quality 第 2 輪 blocker 1；獨立機判腳本全程只印 SHA 前 8 碼、
  size 與命中數，零機密值輸出）。

## 〔review／驗收方法論〕

- **L-192**｜**要量「staged 狀態下某段 hook 的成本」，別為了造 staged 狀態去動真索引或寫新物件**
  ——019 S9 要量 pre-commit 兩段（樣式掃描／值比對）在「純碼 commit」下的成本，而該成本正比於
  staged 內容，故必須有一個真的 staged 狀態。可行且零副作用的作法：`cp .git/index` 到暫存後全程
  帶 `GIT_INDEX_FILE`，並以 `git update-index --add --cacheinfo <mode>,<既有 blob SHA>,<新路徑>`
  把**已在庫的 blob 掛到新路徑**——`git add` 會寫新 blob（＝L-158／L-191 的殘留源），`--cacheinfo`
  掛既有 blob 則**零新物件**，真索引與工作樹全程零改動（機判＝量完 `git status --porcelain` 零行）。
  另一半是「被測工具真的看得到那個索引嗎」：betterleaks 與 `secret-value-guard.py` 皆吃
  `GIT_INDEX_FILE`，機判＝verbose 的 `scanned ~N bytes` 恰等於掛入四檔 byte 數總和（本輪 41353
  逐字相符），不相符就是量到空索引（＝`.githooks/pre-commit` 註解所載「容器不帶 GIT_INDEX_FILE
  掃 0 bytes 靜默漏報」的同型假象）。
  ｜防法：①量測 harness 造 staged 狀態一律走「暫存 index＋既有 blob `--cacheinfo`」，不用
  `git add`、不用 `git stash`；②每段成本用 `perf_counter` 直接包**單一子行程**連跑 n 次取中位數
  （L-155 禁整鏈差量）；③先驗 harness 保真（掛入 byte 數 vs 工具自報掃描 byte 數）再信數字。
  ｜出處：2026-07-30 019 U6 T037（S9 量測；harness 見單元回報，量完真索引零污染反證通過）。

- **L-193**｜**「驗機密檔尾端無 CR／LF」的最順手寫法（`tail -c1 | xxd`）本身就是印出機密值的
  一個 byte**——byte 級健檢的**輸出形制**與健檢邏輯是兩件事：判準要看末 byte，但**看到**不等於
  **印出**。019 U6 收刀終驗一度以 `tail=<hex>` 逐檔列印，等於把 11 支機密各洩 1 byte 到終端與
  scrollback；同型痕跡在本刀較早備註亦有（T007／T019 記過 age identity 的「末 byte 0x64／0xb4」
  ——判定為低危〔age 加密 identity 之**密文**單 byte、非明文機密〕故不追改，但紀律自本條起收緊）。
  ｜防法：①一切機密相關 byte 級健檢寫成**布林斷言**並只印 True／False 與 byte 數
  （`b[-1] not in (0x0a, 0x0d)`、`b'\r' not in b`），`xxd`／`tail -c1`／`od` 的輸出不得進終端、
  報告或帳本；②比對一律 `sha256sum`／`cmp`／byte 數，需要「指紋」時用 sha256 前 8 碼（雜湊、
  非值切片）；③驗收劇本寫判準時連**輸出形制**一起寫死（「印布林、不印 byte」），否則下一個人
  照最順手的寫法就再洩一次。
  ｜出處：2026-07-30 019 U6 T038 收刀終驗（自我違紀當場改判、改布林斷言重驗 11/11 全綠）。

- **L-197**｜**「收刀終驗」的機判數字寫成恆值，會被同一單元後續 fix 輪次自己的 append 推翻**
  ——019 U6 收單記「`lint` 0 錯誤 0 警告、LESSONS 主卷 21598 tokens＝未逼近、不切卷」，其後三輪
  quality fix 各自又 append 教訓，主卷升到 24783、越過 WARN 22500：全刀最後一道閘的**權威記錄
  與重跑結果相反**。成因＝fix 輪次本身就是改動被量測對象的寫入者（append 教訓、改 BACKLOG／
  NOTES 皆計入配額）。｜防法：①終驗數字標**量測時點**（commit SHA＋「非恆值」），判準寫「以
  現場重跑為準」——★**「全綠／零漂移」這類布林斷言同樣是量測時點值**，須連**基準與終點 SHA
  ＋排除清單**一併寫死；否則下一輪就地勘誤動到被比對的對象，依段重跑者只得到一筆紅、而段內零
  說明（本條第三次復發、載體由數字換成布林）；
  ②判準用**語意式下界**取代「全綠」——★**筆數不入判準**：寫成「0 錯誤＋
  警告集合逐筆具名且各有可行動歸屬（**空集合亦合格**）」，**不可**寫成「恰為 X 那 1 筆」
  （本條初版即這樣寫、當輪就被自己咬：第 4 輪真的把那筆警告消滅了，於是「恰只允許 1 筆」

  ③本輪動過終驗量測對象就**回頭重跑上游終驗**。｜出處：2026-07-30 019 U6 quality 第 3 輪
  blocker 1（`git log -S'21598 tokens'` 只回收單那一筆 commit，後兩輪 append 均未回頭更新）
  ＋收單確認審 blocker 2／3（本條防法②初版之「恰為 1 筆」寫法在 quickstart §S10 與 tasks
  T038 兩處被同刀分卷推翻，一併改為空集合亦合格）＋同確認輪之 T038「逐筆 byte 級零漂移經獨立
  重跑全綠」被本條自身的就地勘誤推翻（→防法①擴及布林斷言、該段補兩端基準標定與排除清單）。

## 〔機密與落點接線（SOPS／SECRETS_DIR／解析口徑）〕

- **L-176**｜**寫檔守住 byte-identical，讀取比對卻用命令替換＝不變式在比對面破功**——019 機密檔
  一律 `printf '%s'` 寫入（零尾端換行）並立 CR 護欄，但 preflight 的 composite↔leaf 一致性
  與 generate 的 dual-write drift 判定都用 `[ "$(cat f)" = "$v" ]`：命令替換會剝掉尾端換行，
  於是「檔尾多一個 LF」這一格對兩者**結構性失明**——實測 `redis_password.txt` 尾多一個 LF
  （15 byte、健康值 14 byte）時 preflight 仍回「齊備且健康、可 up」`rc=0`，compose 卻會把
  15 byte 密碼掛進 redis、把內嵌 14 byte 版本的 `redis_url` 掛進 rust-api＝認證必失敗而
  上機前的 fail-loud 承載者放行；generate 同情境印 SKIPPED、劣化不修復。尾端換行正是編輯器
  覆存最常見的產物（與 CRLF 同一個編輯器、同一次覆存），而護欄當初只立了 CR 那一半。
  ｜防法：①位元組不變式的檢查也要走位元組——`printf '%s' "$v" | cmp -s - "$f"`，不用
  `$(cat)` 字串相等（decrypt 當時已是這個形，是三支消費者裡唯一真的在驗位元組的）
  ②護欄要對著**不變式**寫、不要對著**單一已知劣化樣本**寫：CR 護欄的判準若寫成「零換行
  字元」（`stat -c %s` ＝ 剝除 CR／LF 後 byte 數），LF 這格從一開始就在射程內
